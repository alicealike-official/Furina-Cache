# 28nm 600MHz 频率目标与优化建议

> 版本：v1.0  
> 日期：2026-11-13  
> 状态：**验证优先**。本文只记录后续频率优化的判断与候选方案，不作为当前 RTL 的实现要求。  
> 适用对象：带 MSHR 的非阻塞 D-Cache（当前 2 级流水实现）  
> 目标：28nm 工艺，600 MHz（周期约 1.667 ns）  
> 依据文件：`Design/DCacheMSHR/src/main/scala/furina/dcache/` 下的 `DCache.scala`、`CacheMem.scala`、`Mshr.scala`、`WriteBackBuffer.scala`、`ReplacePolicy.scala`、`Ram2R2W.scala`

---

## 1. 结论摘要

1. 当前 2 级流水结构在 28nm LP/LP+ 下，粗估 **300–500 MHz**，中心值约 **400 MHz**；28nm HPC/HPA 下可能到 **400–600 MHz**。
2. 600 MHz 是**有希望达到的**，但需要针对关键路径做优化，不能指望直接综合就收敛。
3. 最可疑的三条路径：
   - **跨 Stage2→Stage1 的 `s2Stuck → cpuReady → accept` 组合路径**；
   - **`policy.allocWay → victimWay → victimTag → WBB/MSHR` 的淘汰路径**；
   - **R1 数据选择：16:1 word mux → 4:1 way mux → bypass → FIFO push**。
4. 优化优先级建议：
   - **结构性首选**：**请求侧 FIFO 解耦**（与响应侧对称），去掉 Stage1 的 MSHR 匹配和 `s2Stuck → cpuReady` 长路径。
   - **P0 微优化**：如果暂时不加请求 FIFO，先打断 `s2Stuck → cpuReady`；把 victim 选择从 128:1 动态 mux 改为每 set 寄存器/指针。
   - **P1**：拆 Stage2（hit/victim 与 commit 分级）；数据 mux 分级或寄存。
   - **P2**：消除 `lockMask`、`policy_order`、`validBits` 的大动态索引 mux；确认 SRAM 推断/宏。
   - **P3**：布局布线、时钟树、线延迟优化。
5. 任何改变流水级数、命中延迟、冻结时序的优化，都会影响验证计划和后门路径；必须先完成当前功能验证，再按本文顺序迭代。
6. 最准的做法：先用目标 28nm 库、600 MHz 约束综合一次，看 `report_timing` 的真实关键路径；本文的估算是**数量级参考**，不是签核结论。

## 2. 估算前提

本文估算基于以下假设：

| 项目 | 假设 |
| --- | --- |
| 工艺 | 28nm LP / LP+ / HPC / HPA，标准单元库 |
| 电压/温度 | 典型 TT/0.9V/25C（HPC）或 TT/0.9V/25C（LP） |
| 综合 | Design Compiler / Genus，基本时序约束，无手工重定时 |
| 存储体 | tag/data 用小 SRAM 宏，或被综合为 register file |
| 流水 | 当前 2 级：Stage1 接收/检查，Stage2 命中/提交 |
| 时钟 | 理想时钟，预留 100–150 ps skew/uncertainty |
| 互连 | 初步布局，未做手工 floorplan |

实际频率会受标准单元库、VT 混合、SRAM 宏 access time、布局布线、时钟树和约束质量影响，可能有 ±30% 偏差。

## 3. 当前频率粗估

| 工艺档位 | 预期频率 | 说明 |
| --- | --- | --- |
| 28nm ULP/ULP+ | 250–400 MHz | 低功耗库，慢速 corner 更差 |

| 28nm HPC | 400–600 MHz | 高性能库，需时序优化 |
| 28nm HPA | 500–650 MHz | 高性能高密度，优化后可接近 600–700 MHz |

## 4. 关键路径分析

### 4.1 跨 Stage2→Stage1：`s2Stuck → cpuReady → accept`

相关代码：

- `DCache.scala`：
  - `s2StuckCond` 的组合条件；
  - `val s2Stuck = s1Valid && s2StuckCond`；
  - `io.cpu.ready := !s2Stuck && cpuReadyComb`；
  - `val accept = io.cpu.valid && io.cpu.ready`；
  - `cache.io.r1.en := accept || s2Stuck`。

路径组成：

```text
tag SRAM 输出
  → hitVec / hit（21-bit 比较 + 4 路 OR）
  → hitMshr / canMerge / wbb.q1Same / reserveFail
  → s2StuckCond
  → s2Stuck
  → io.cpu.ready
  → accept
  → cache.r1.en / s1* 寄存器使能
```

此外 `s2StuckCond` 还包含：

- `needEvict && (!mshr.hasFree || !hasVictim)`；
- `!hit && wbb.q1Same`（4 × 32-bit 地址比较）；
- `reserveFail`（WBB 预留失败）；
- `respFullAny`（两个 FIFO 的 full）。

这是当前设计最长的跨级组合路径，粗估 **2.0–3.0 ns**。如果 28nm LP 下周期只有 2.2–2.5 ns，这条路径会直接限制频率。

### 4.2 淘汰路径：`policy.allocWay → victimWay → victimTag → WBB/MSHR`

相关代码：

- `DCache.scala`：
  - `val policyWay = policy.allocWay(s1Index, lock1)`；
  - `val victimWay = Mux(hasEmpty, emptyWay, policyWay)`；
  - `val victimTag = cache.io.r1.tag(victimWay)`；
  - `val victimBlockAddr = blockAddrFromTagIndex(victimTag, s1Index)`；
  - `wbb.io.reserve.addr := victimBlockAddr`；
  - `mshr.io.alloc.way := victimWay`；
  - `cache.io.clr.way := victimWay`。
- `ReplacePolicy.scala`：
  - `order(setIndex)(i)` 是 32 set × 4 way 的 2-bit 动态索引；
  - `priorityLowest` 选择第一个未锁定路；
  - `moveToTail` 在 fill/hit 时更新 order。

路径组成：

```text
s1Index 寄存器
  → policy_order 32×4 动态 mux（128:1）
  → priorityLowest / lockMask 过滤
  → policyWay
  → victimWay
  → victimTag 4:1 mux
  → victimBlockAddr
  → WBB reserve addr / MSHR alloc / cache clr
```

粗估 **1.5–2.2 ns**。其中 `order(setIndex)(i)` 的 128:1 mux 和 `priorityLowest` 是主要延迟；如果综合工具把它实现成多级 mux + 优先级树，延迟会更高。

### 4.3 R1 数据选择：16:1 word mux → 4:1 way mux → bypass

相关代码：

- `CacheMem.scala`：
  - `val wordOut = Vec((0 until wordsPerBlock).map(word => banks(w)(word).rd1Data))`；
  - `io.r1.data(w) := wordOut(rdWordOffPipe)`（16:1 mux）。
- `DCache.scala`：
  - `val hitReadData = Mux(bypass, p1Data, cache.io.r1.data(hitWay))`（4:1 mux + bypass）；
  - `rdFifo.io.push.payload.rData := Mux(hitRead, hitReadData, replay.payload.rData)`。

路径组成：

```text
bank 读输出寄存器
  → 16:1 word mux（rdWordOffPipe）
  → 4:1 way mux（hitWay）
  → bypass 2:1 mux
  → rdFifo push 逻辑
```

粗估 **0.8–1.2 ns**。单独看不算最长，但它和 tag 比较/priority 并行，若数据 mux 与 FIFO push 同拍完成，会叠加到 Stage2 的周期里。

### 4.4 Stage1：MSHR match + WBB 检查 + lockMask

相关代码：

- `Mshr.scala`：`buildMatch` 对 4 个 entry 做 tag/index 比较，`priorityLowest` 选 entry，`slotFree` 是 4 slot valid 的动态 mux。
- `WriteBackBuffer.scala`：`sameAddr` 对 4 个 slot 做 32-bit 地址比较；`full` 是 4 slot 的 OR。
- `DCache.scala`：`lock0` 从 `mshr.io.lockMask(cpuIndex)` 动态取 4 路；`hasWay0 = !lock0.andR`。

路径组成：

```text
cpuTag/cpuIndex
  → 4 × (21-bit tag 比较 + 5-bit index 比较)
  → priorityLowest → entry
  → slotFree 4:1 mux
  → canMerge0
  → missPath0
  → cpuReadyComb
```

另外 `lock0` 是对 `lockMask` 的 32×4 动态索引，综合后是一个 32:1 mux（每路），也会贡献延迟。

粗估 **1.5–2.2 ns**。单独看不算最长，但它与 4.1 的 `s2Stuck` 叠加后，`cpuReady` 路径会更长。

### 4.5 fill / replay 的数据合并

相关代码：

- `Mshr.scala`：
  - `mergedLine(e)`：16 words × 4 slots 的 mux，按 `slotValid && slotIsWrite && slotWordOff == w` 覆盖 `entryFillData`；
  - `slotRData(k)`：每个 slot 对前序 slot 的同字写做 mux；
  - `io.fill.line := mergedLines(fillIdx)`；
  - `io.replay.payload.rData := slotRData(replaySlotAddr)`。

路径组成：

```text
entryFillData / slotWData
  → 16 words × 4 slots mux
  → fillIdx mux（4:1）
  → cache.w2.line
```

以及：

```text
slotWData / slotWordOff / slotValid
  → slotRData 16×4 mux
  → replaySlotAddr 16:1 mux
  → replay.payload.rData
```

粗估 **1.0–1.8 ns**。fill 和 replay 不是每个命中请求的关键路径，但它们是 W2 写口和重放响应的路径；如果同拍还要做 WBB/MSHR 提交，可能成为次关键路径。

| 优先级 | 优化项 | 预期收益 | 代价/风险 | 对验证的影响 |
| --- | --- | --- | --- | --- |
| **P0（结构性）** | **请求侧 FIFO 解耦**（方案 A） | 可能 +150–250 MHz | 增加 2–4 深小 FIFO；FIFO 非空时命中延迟增加 | 高：ready 语义、HIT/STC/BP/RSQ、后门路径 |

### 5.0 结构性方案：请求侧 FIFO 解耦（推荐优先评估）

#### 动机

响应侧已经有 `rdFifo`/`wrFifo`，把“响应产生”和“CPU 取走响应”解耦；请求侧目前没有对应的缓冲，CPU 的 `ready` 直接依赖 Stage1 的组合检查，而 Stage1 又要看 Stage2 的 `s2Stuck`。这造成两个问题：

- Stage1 必须重复做 MSHR 匹配、WBB 同地址/满、lockMask、可用 way 等检查；
- `s2Stuck → cpuReady → accept` 成为跨 Stage1/Stage2 的长组合路径。

既然响应侧可以用 FIFO 解耦，请求侧也可以对称地放一个 FIFO：

```text
CPU → [reqFifo / fall-through] → Stage1（只做地址分解 + 发 R1） → Stage2（唯一权威判定 + 提交）
```

与响应侧对称地看：

```text
          ┌──────────┐    ┌────────┐    ┌────────┐    ┌──────────┐
CPU ─────>│ reqFifo  │───>│ Stage1 │───>│ Stage2 │───>│ respFifo │───> CPU
          └──────────┘    └────────┘    └────────┘    └──────────┘
              请求解耦         流水          提交          响应解耦
```

请求 FIFO 负责“接收”和“提交”的解耦，响应 FIFO 负责“产生”和“取走”的解耦；两侧都不再把 CPU 握手压进 Stage2 的组合路径。

#### 结构

- `reqFifo` 深度 2–4，payload 为 `addr/wrEn/wData/id`，可选携带预分解的 `tag/index/wordOff/blockAddr`；
- Stage1 从 `reqFifo` 头部取请求，只做地址分解和 `cache.r1` 读地址驱动，不再做 MSHR 匹配/资源检查；
- Stage2 做唯一一次 Cache tag 比较、MSHR 匹配、WBB 同地址/满、victim/policy、lock 检查，并提交；
- `cpu.ready = reqFifo.io.push.ready`（即 FIFO 未满；可选再加少量**寄存器化**全局标志）；
- Stage2 不能提交时，只停 `reqFifo` 的 pop 和 Stage1/Stage2 流水寄存器，不再组合反压 `cpu.ready`；
- FIFO 满后，CPU 自然被反压。

伪代码：

```scala
val reqFifo = StreamFifo(CpuReq(cfg), REQ_QUEUE_DEPTH) // 需要 bypass/fall-through 模式
reqFifo.io.push << io.cpu

val head = reqFifo.io.pop.payload
// Stage1：从 FIFO 头部驱动 R1 和 s1* 寄存器
val popFire = reqFifo.io.pop.valid && reqFifo.io.pop.ready
reqFifo.io.pop.ready := !s2Stuck

cache.io.r1.en := popFire || s2Stuck
cache.io.r1.index := Mux(s2Stuck, s1Index, indexOf(head.addr))
cache.io.r1.wordOff := Mux(s2Stuck, s1WordOff, wordOffOf(head.addr))

when(popFire) {
    s1Valid := True
    s1Tag := tagOf(head.addr)
    // ... 其余 s1* 字段
} elsewhen (s1Valid && !s2Stuck) {
    s1Valid := False
}
```

注意：`s2Stuck` 仍然存在，但它只控制 FIFO pop 和写使能，不再出现在 `io.cpu.ready` 的组合路径上。

#### 为什么能提高频率

- 去掉 Stage1 的 4 条目 MSHR 匹配、WBB same/full、lockMask、policy 选择等组合逻辑；
- 打断 `s2Stuck → cpuReady` 这条跨级路径；
- `cpu.ready` 只依赖 FIFO 的 `push.ready/full`，是一个短路径；
- Stage2 仍然是权威阶段，但它的输出只控制 FIFO pop 和写使能，不再回送到 CPU ready。

#### 命中延迟

- 如果 FIFO 是 **fall-through / bypass** 结构，且 FIFO 为空：新请求当拍穿过 FIFO 进入 Stage1，命中延迟仍是 2 拍；
- 如果 FIFO 非空：新请求排队，命中延迟增加 FIFO 占用拍数；
- 这与响应侧 FIFO 的行为对称：CPU 观察到的延迟本来就是“内部延迟 + 排队 + 反压”，不是恒定值。

#### 可选的 Stage1 准入控制

如果担心 FIFO 经常被 Stage2 的慢路径填满，可以在 Stage1 保留少量**寄存器化**的全局标志：

- `mshrHasFreeR`：MSHR 有空条目；
- `wbbNotFullR`：WBB 未满；
- `respQueueNotFullR`：响应队列未满。

这些标志只用于“提前挡一下”，不要求精确；如果标志说可用但 Stage2 发现不可用，FIFO 会吸收这个请求，Stage2 冻结等待，正确性不受影响。不要把这些标志做成 4 条目匹配/32 位地址比较那种长组合逻辑。

#### 代价与风险

- 多一个 2–4 深的小 FIFO（面积很小，但增加控制）；
- 资源紧张时 FIFO 会填满，CPU 被反压的时机比现在晚；
- 命中延迟在 FIFO 非空时变长；
- 需要重新验证 ready 语义、FIFO 满/空、头阻塞、请求顺序、与响应 FIFO 的联合反压；
- Stage2 仍然需要冻结逻辑，但它只影响 FIFO pop/写使能，不影响 CPU ready；
- 请求 FIFO 满本身不会引入新的内部死锁：它和响应 FIFO 一样，只依赖 CPU 最终取走响应；只要 CPU 不永久停止取响应，反压就能解除。

#### 对验证的影响

新增/修改的验证点：

- **REQ-001**：请求 FIFO 复位空、满/空标志正确；
- **REQ-002**：FIFO 满时 `cpu.ready=0`，不满时恢复；
- **REQ-003**：fall-through 路径：FIFO 空时新请求不被多挡一拍；
- **REQ-004**：FIFO 非空时请求按序处理，无丢失/重复/乱序；
- **REQ-005**：Stage2 长冻结期间 FIFO 填满，解除后恢复，T1/T2 正确；
- **REQ-006**：请求 FIFO 与响应 FIFO 同时接近满时的反压组合，无死锁；
- **REQ-007**：FIFO 上溢/下溢 SVA，push/pop 同拍正确。

受影响的原验证点：

- **STC-006/007**：`cpuReady` 不再直接包含 MSHR/WBB/资源条件，改为“FIFO 满”行为；
- **BP-001/002**：反压因子从 `cpuReady` 组合项变成“FIFO 填满”；
- **HIT-001/006/008、PERF-005**：命中延迟在 FIFO 非空时变化；
- **T1/T2**：请求顺序/响应匹配仍然成立，但延迟分布变化；
- **后门路径**：新增 `reqFifo.io_occupancy`、`push/pop`、`head/tail` 等观测点。

#### 实现提示

- 用 `StreamFifo` 的 bypass/fall-through 模式，或自己写 2 深度 skid buffer；不要用普通非 bypass FIFO，否则空队列也会多一拍；
- Stage1 的 `s1*` 寄存器仍然保留，作为 FIFO 头部到 Stage2 的流水寄存器；
- `reqFifo.io.pop.ready := !s2Stuck`，确保 Stage2 冻结时头部不丢；
- `io.cpu.ready := reqFifo.io.push.ready`，`reqFifo.io.push.valid := io.cpu.valid`；
- 注意 FIFO 满时 `io.cpu.valid` 可能仍然为高，必须满足 valid/ready 契约：FIFO 满时不能 pop，CPU 保持 payload 稳定。

### 5.1 P0：打断 `s2Stuck → cpuReady`

候选方案：

1. **寄存 `s2Stuck`**  
   ```scala
   val s2StuckR = RegNext(s2Stuck, False)
   io.cpu.ready := !s2StuckR && cpuReadyComb
   ```
   代价：冻结进入/退出可能多一拍 bubble；需要重新定义 ready 协议和验证点。

2. **拆分 `cpuReady` 为 estimate/final 两级**  
   Stage1 只做保守估计，Stage2 用 skid buffer 处理“已接收但无法提交”的情况；复杂度较高，但可以保持吞吐。

3. **把 hit/victim 判定提前到 Stage2a 并寄存**  
   见 5.2/5.3，等于拆 Stage2。

建议：优先评估方案 1 的协议代价；如果 bubble 可接受，这是最小的改动。

### 5.2 P0：victim 选择寄存化

当前 `policy.allocWay` 在 Stage2 组合计算 128:1 mux + priority。可以改为：

- 每个 set 维护一个 `victimWayReg`（2 bit），在 fill/hit/evict 时更新；
- Stage2 直接读 `victimWayReg(s1Index)`，只做 32:1 的 2-bit mux；
- `lockMask` 仍然参与过滤，但可以并行计算，或维护每 set 的 lock 位；
- 对 FIFO 策略，`victimWay` 就是 `order(s)(0)`；对 LRU，是队头；对 PLRU，可以提前算好并寄存。

注意：`wayLocked` 是动态的，`victimWayReg` 必须在锁变化时重新选择；建议保留一个小的“跳过锁定路”的 4:1/priority 逻辑，但不要放在 128:1 mux 之后。

验证影响：

- RST-003 的策略初值；
- RPL-002/003/004 的 onHit/onFill 契约；
- RPL-005/006/007/008/009 的 lock/victim 行为；
- INV-4/5 的锁与条目对应关系。

### 5.3 P1：拆 Stage2

当前 Stage2 同时做：

- tag 比较、hitWay；
- MSHR match/mergeable；
- victim 选择、WBB reserve；
- W1/W2/CLR/R2 使能；
- policy onHit/onFill；
- 响应入队。

可以拆为：

- **Stage2a（判定）**：hit/hitWay、hitMshr/canMerge、victimWay/victimDirty、wbb.q1Same、reserveFail；结果打拍。
- **Stage2b（提交）**：W1/W2、WBB reserve/push、MSHR alloc/merge、policy 更新、响应入队。

代价：

- 命中延迟从 2 拍变 3 拍；
- 需要增加一级流水寄存器；
- 冻结/旁路/重放时序都要重新定义；
- 验证计划中的时序图、HIT-001/006/008、BYP、STC、MSH、RSQ 都要更新。

收益：Stage2 的组合深度减半，28nm 下更容易到 600 MHz。

### 5.4 P1：数据 mux 分级

当前 `CacheMem` 是 16 个 word bank 输出直接做 16:1 mux，再在 `DCache` 做 4:1 way mux。可以：

- 把 16:1 拆成 4 组 4:1 + 一级 4:1；
- 或在 bank 输出后加一级寄存器，把 16:1 mux 放到下一拍（会增加命中延迟）；
- 或把 word bank 组织成 4 个 group，每组共享一个 4:1 mux，减少长线。

注意：如果加寄存器，命中延迟会变，必须同步验证计划。

### 5.5 P2：消除大动态索引

- `lockMask`：当前是 32×4 的矩阵，DCache 用 `cpuIndex`/`s1Index` 动态索引。可以改为从 4 个 MSHR entry 的 `entryIndex/entryWay` 直接比较出当前 set 的 4 位 lock，避免 32×4 矩阵 + 32:1 mux。
- `policy_order`：32×4 的 2-bit 矩阵；改为每 set 的寄存器/小 RAM，或按 set 分组，减少 mux。
- `validBits/dirtyBits`：32×4 的 Reg Vec；`inspect` 的动态索引是 4 个 32:1 mux。可以保持，但注意它和 `hit` 路径是分开的（hit 用的是 R1 打拍后的 valid/dirty），不要误优化到关键路径上。

### 5.6 P2：SRAM 推断/宏

- 确认 tag/data 是被综合成 SRAM 还是 register file；
- 对 32×32 的小 bank，register file 可能更合适；不要盲目追求 SRAM 宏；
- 如果使用 SRAM 宏，确认 access time 和 write mask 支持；
- 如果使用 `Ram2R2W` 四副本，注意 2:1 recency mux 和四份阵列的布线延迟。

### 5.7 P3：后端

- 64 个 bank + tag 阵列的布局要靠近数据 mux，避免长线；
- 时钟树要平衡，特别是 `s1Index`、`hitWay`、`victimWay` 这些高扇出信号；
- 对 `cpuReady`、`s2Stuck` 这类高扇出控制信号做 buffer/复制；
- 预留 clock uncertainty 和 I/O delay。

## 6. 推荐路线

### 阶段 0：先完成功能验证（当前）

- 不改流水结构、不改时序；
- 用当前 RTL 跑通 UVM 回归、覆盖率、SVA；
- 把本文作为“后续优化候选清单”，不进入当前 RTL。

### 阶段 1：综合测量

1. 用目标 28nm 库、600 MHz 约束（1.667 ns）综合当前 RTL；
2. 看 `report_timing` 的 top 20 路径；
3. 按本文第 4 节分类，确认哪条是真实关键路径；
4. 记录频率、面积、功耗基线。

### 阶段 2：结构性优化（优先评估请求侧 FIFO）

- 先评估 5.0 的请求侧 FIFO 解耦；如果 FIFO 面积/延迟可接受，优先实施；
- 如果不采用 FIFO，再按 5.1/5.2 做 P0 微优化：
  - 打断 `s2Stuck → cpuReady`；
  - victim 选择寄存化；
- 重新综合，评估频率/面积/验证影响。

### 阶段 3：P1 优化

- 如果 P0 还不够，拆 Stage2 或数据 mux 分级；
- 同步更新验证计划、SVA、后门路径、时序图。

### 阶段 4：P2/P3 优化

- 消除大动态索引；
- SRAM/register file 选择；
- floorplan/时钟树。

## 7. 对验证的影响

任何频率优化都可能改变以下内容，必须同步更新验证计划：

| 优化 | 受影响验证点/断言 | 说明 |
| --- | --- | --- |
| **请求侧 FIFO** | **REQ-001~007、STC-006/007、BP-001/002、HIT-001/006/008、PERF-005、T1/T2** | **CPU ready 只看 FIFO 满/空；命中延迟在 FIFO 非空时变化；需新增请求 FIFO 断言/覆盖率** |
| 寄存 `s2Stuck` | T1/T2、STC-001~007、BP-001/002、RSQ-002/003 | ready 时序变化，可能多 bubble |
| 拆 Stage2 | HIT-001/006/008、BYP-001/002/003、MIS-009、MSH-010/013、RSQ-003、PERF-005 | 命中延迟、冻结窗口、重放时序变化 |
| victim 寄存化 | RST-003、RPL-002~009、INV-4/5 | 策略状态/锁语义必须等价 |
| 数据 mux 分级 | HIT-001/006、BYP-001/002 | 可能增加命中延迟 |
| `lockMask` 重写 | RPL-009、INV-4/5、MSH-018/019/020 | 锁与条目一一对应 |
| SRAM/blackbox | 后门路径、GLS | 内部数组名可能变化，需更新路径表 |

后门路径表也要随流水寄存器/实例名变化更新；不要在优化时悄悄改名字。

## 8. 先测量，再优化

本文的频率估算是**前综合数量级判断**，不是签核结论。实际关键路径可能和本文不同，原因包括：

- 标准单元库的驱动能力/阈值电压；
- SRAM 宏的 access time 和 write mask；
- 综合工具的 mux/priority 实现；
- 布局布线后的线延迟；
- 时钟树和 uncertainty；
- 约束是否合理。

因此建议：

1. **不要在没有综合报告的情况下按本文直接改 RTL**；
2. 先跑一次 600 MHz 综合，拿到真实 critical path；
3. 如果真实关键路径与本文第 4 节一致，再按“结构性方案（请求侧 FIFO）→ P0 → P1 → P2”的顺序优化；
4. 每次优化都记录频率、面积、功耗和验证影响。
