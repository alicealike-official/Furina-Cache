# WBB-DUT-001：发送背压期间，新候选替换了尚未握手的请求

记录日期：2026-11-19。WBB 设计源码和 C++ 参考模型均已补上背压保持。现有 UVM 的 26 组回归全部通过，用例、断言、驱动和回归脚本未修改。

## 问题是什么

WBB 已经把一笔请求放到 `send` 接口上，`send_valid=1`，但内存暂时不接收，`send_ready=0`。这时请求还没有握手，WBB 必须继续保持同一笔请求，直到接收方准备好。

原实现会在等待期间重新计算发送候选。另一个槽刚刚完成 push 后，可能变成轮询中更靠前的候选，从而抢走出口。定向测试里，原先等待的 ID 3 被 ID 0 替换，地址和整行数据也一起变化。

这个场景最终仍能把两笔数据都写回，所以仅检查最终内存内容看不出问题。错误发生在接口等待期间：已呈现但尚未被接收的请求发生了变化。

## 为什么轮询指针没变，输出却变了

在当前实现中，`rrPtr` 表示“下一次扫描从哪个槽开始”，并不保存“当前已经选中了哪个槽”。这是代码采用的内部语义，不是 spec 对指针名称的强制定义。原实现用以下步骤实时选择输出：

1. 把 `valid && !issued` 的槽列为候选。
2. 从 `rrPtr` 开始环形扫描，找到第一个候选。
3. 用这个槽号直接选择输出的地址、数据和 ID。

例如 `rrPtr=0` 时，如果只有槽 3 待发，扫描结果就是槽 3。此后即使 `rrPtr` 仍为 0，只要槽 0 也成为候选，扫描结果就变成槽 0。因此，“握手前不更新轮询起点”不足以保证“握手前不更换请求”。缺少的是对已经呈现的选择结果进行保持。

源码位置：[WriteBackBuffer.scala](../../Design/DCacheMSHR/src/main/scala/furina/dcache/WriteBackBuffer.scala)。原发送仲裁直接将组合计算出的 `sendIdx` 用于输出，没有挂起选择的寄存器。

## ID 3 怎样变成 ID 0

下表来自修复前 10 ns 时钟定向测试的沿前采样。`word0` 是整行数据的最低 32 位，便于辨认两笔不同请求。

| 时间 | 事件 | send valid/ready | 输出 ID | 地址 | word0 |
| --- | --- | --- | --- | --- | --- |
| 185 ns | 初始槽 3 的请求完成发送，轮询起点回绕到 0 | 1/1 | 3 | 0x100 | 0x00040000 |
| 205 ns | 旧槽 3 收到响应，得以释放 | 0/0 | 无有效请求 | — | — |
| 215、225 ns | 重新预留槽 3，下一拍 push 新行 | 0/0 | 无有效请求 | — | — |
| 235～265 ns | 槽 3 的新请求等待内存接收 | 1/0 | 3 | 0x140 | 0x00050000 |
| 275 ns | 旧槽 0 收到响应，得以释放 | 1/0 | 3 | 0x140 | 0x00050000 |
| 285 ns | 为另一笔新请求预留槽 0 | 1/0 | 3 | 0x140 | 0x00050000 |
| 295 ns | 合法 push 槽 0；这个沿之后槽 0 加入候选 | 1/0 | 3 | 0x140 | 0x00050000 |
| 305 ns | 没有发送握手，输出却已被替换 | 1/0 | 0 | 0x180 | 0x00060000 |

实际切换发生在 295 ns 沿后，305 ns 沿前采样捕获变化。235～325 ns 连续 10 个采样沿的 `send_ready` 都是 0，期间不存在允许切换请求的发送握手。

槽 0 是在旧响应释放后才重新预留，push 也在预留的下一拍发生，地址不同且按行对齐，因此输入符合约定。这不是测试环境非法覆盖槽 3，也不是槽 3 的存储数据被改写，而是输出选择从槽 3 切到了槽 0。

## 原规格已经要求保持

[Cache 架构设计文档 v2 §4.6](../Cache架构设计文档v2.md#46-握手与反压)已经规定所有流在背压时保持 valid 和载荷，直到握手后才可改变。因此这属于实现缺陷，已有规格足以判定错误。

[WBB IP 架构设计文档 §8.2](../WBB_IP架构设计文档.md#82-请求保持与仲裁锁定)已经明确规定：`send_valid=1 && send_ready=0` 之后，下一采样沿必须继续保持 valid、地址、数据和 ID；新槽 push 或更靠前候选出现，都不能替换已呈现请求。

因此，本次修复落实既有接口要求，不改变上游 reserve/push 的使用方式，也不要求下游接受会变化的挂起请求。恢复 `ready=1` 的那个握手沿仍须交付原请求，不能提前换成新候选。

## 修复方式

保留现有轮询选择，增加“正在保持一个待接收请求”的状态和对应槽号：

- 没有挂起请求时，照常从 `rrPtr` 开始选择候选。
- 某个采样沿出现 `send_valid && !send_ready` 时，记住该请求的槽号。
- 后续只要还未握手，就继续从这个槽输出地址、数据和 ID。新候选仍可进入 WBB，但不能抢占当前出口。
- 真正发生 `send_valid && send_ready` 时，才把实际发送的槽标为 `issued`，将轮询起点更新到该槽的下一槽，并清除保持状态。
- 复位清除保持状态，避免保留复位前的选择。

只保存槽号就能保持整笔请求，是因为合法生命周期下，等待发送的槽不会被重复预留或 push，也不会在尚未发送时收到写响应。地址和数据已经保存在该槽中，无须再复制整行数据。握手后即可重新仲裁，连续就绪时仍可连续发送，不必人为插入空拍。

## 参考模型为什么也要修改

原 C++ 参考模型采用相同的“每拍从轮询起点重新选择候选”方式，所以本次错误发生时，它能与错误的 DUT 输出一致。模型比较通过只能证明两者一致，不能证明符合接口规格。

最初只修复 DUT 时，DUT 保持 ID 3，旧模型却预测 ID 0，逐拍比较因此报告 `WBB_SEND`。两者接受的槽号不同，还会使模型的 issued 记录与实际响应不一致，延迟 push 用例因此在模型侧提前终止。

[RefModel/Cache/WriteBackBuffer.hpp](../../RefModel/Cache/WriteBackBuffer.hpp) 现已按同一规格补上 `sendHold_` 和 `sendHoldIdx_`。`tick()` 先读取沿前请求，再决定锁定或完成握手，最后处理新 push。`sendReq()` 在锁定期间返回记住的槽，实际握手时才清除保持并更新该槽的 issued 和轮询起点；reset 清除保持状态。同拍 push 的新候选不能抢占旧请求，多次查询模型输出也不会提前改变状态。

独立协议检查继续保留原要求：[scoreboard](../../verif_mshr/src/wbb/component/scoreboard/wbb_scoreboard.sv)逐拍检查 valid、地址、数据和 ID；[IO SVA](../../verif_mshr/src/wbb/bind/wbb_io_assertions.sv)检查上一拍背压后下一拍仍保持请求，包括 ready 恢复的握手拍。不能通过放宽这些检查来让回归通过。

## PPA 方案比较与待定事项

**状态：暂不选型，本节只记录讨论，不修改当前 RTL、参考模型或验证环境。** 当前独立保持方案已通过现有 26 组功能回归；下面两种替代方案尚未实现或验证。比较以默认 4 槽、512 位行宽为背景，没有综合、静态时序或布局布线结果，因此只说明结构上的取舍，不承诺具体面积、频率和功耗收益。

### 先区分规格要求和指针实现

[Cache 架构文档 §8.6](../Cache架构设计文档v2.md#86-发送仲裁)要求轮询发送和公平性，没有明确规定某个 ptr 寄存器必须保存下一笔实际请求的槽号。[WBB IP 规格 §12.1](../WBB_IP架构设计文档.md#121-轮询公平性)也说明不规定初始轮询起点或精确候选编码，并要求挂起请求保持原选择。

因此，“指针保存扫描起点”和“指针直接保存选中的请求”都是可以评估的实现方式。原实现缺少背压保持是明确的规格违约；使用 `rrPtr + rotK` 寻找候选本身并不违反现有规格。不能仅凭寄存器名字认定某一种组织方式才符合 spec。

当前代码中的 `rotK` 是从扫描起点走到第一个可发送槽的相对偏移：`候选槽号 = (rrPtr + rotK) mod N`。例如 rrPtr=0、只有槽3待发时，rotK=3；槽0加入后，rotK变成0。这也是只保持扫描起点仍不足以保持输出请求的原因。

### 三种实现分别记住什么

| 方案 | 如何保持请求 | 面积倾向 | 时序与控制代价 |
| --- | --- | --- | --- |
| A 独立保持状态，当前实现 | rrPtr 保存轮询起点，sendHoldIdx 单独保存被背压的请求槽号 | 增加少量控制寄存器和索引选择逻辑 | 组合仲裁后还有一次 hold 选择；控制职责分开，已通过功能回归 |
| B 复用 rrPtr 锁住当前赢家 | 背压沿把 rrPtr 设为当前选中槽，握手后再设为该槽加一 | 可省去独立保持状态和最终索引选择 mux，控制面积倾向更小 | 输出仍经过组合仲裁；指针兼有轮询起点和保持职责 |
| C 寄存发送槽号，直接选择输出 | 寄存器直接保存当前有效请求的槽号，另算下一候选 | 需要有效状态和下一候选控制，面积取决于具体组织 | 可缩短输出选择路径，但需要处理启动延迟、连续发送和下一状态计算 |

方案 B 不等于“仅把 rrPtr 更新条件改成握手”。原代码已经只在握手时推进 rrPtr；方案 B 还需要在背压沿把 rrPtr 写成当前赢家。其行为可以表示为：

```text
没有有效请求：保留 rrPtr
有效但未握手：rrPtr ← 当前选中的槽
实际握手：   rrPtr ← 当前选中的槽 + 1，按槽数回绕
```

例如槽3被背压后，rrPtr变成3。下一拍从槽3开始扫描，槽3仍是 valid 且未 issued，因此偏移0就命中；槽0即使加入也不能抢占。首次背压与其他槽push同沿发生时，记录的仍是沿前已呈现的槽号。

这个推理依赖现有合法输入约束：待发送槽在握手前不能被重复push、取消或提前响应释放。若以后增加取消或更新待发请求的功能，需要重新检查此方案。

### 面积收益主要在控制部分

默认四槽时，方案 A 的保持状态是 1 位 sendHold 和 2 位 sendHoldIdx，共 3 位寄存器，并有一个 2 位索引的二选一 mux。这里没有额外增加一整条 512 位数据保持寄存器，也不是额外增加一个 512 位 hold mux。

方案 B 可以省去这 3 位状态及索引选择逻辑，但会改变 rrPtr 的更新逻辑。WBB 仅行数据存储就有 4×512=2048 位，所以这是控制部分的小优化，不能把省下几个控制位直接换算成整个模块的大幅面积下降。最终仍要看综合如何映射、共享和优化逻辑。

### 时序收益取决于仲裁放在哪里

方案 A 从状态到发送载荷的逻辑路径大致为：

```text
候选状态 / rrPtr → 旋转候选 → 优先编码 rotK → 计算候选槽号
               → hold 索引选择 → 槽地址和 512 位数据选择 → send 输出
```

方案 B 去掉最终 hold 索引选择，但旋转、优先编码和槽号计算仍然位于输出选择之前，因此不能把它视为彻底切断仲裁路径。

方案 C 的输出路径可以变为：

```text
已寄存的发送槽号 → 槽地址和 512 位数据选择 → send 输出
```

这更有利于缩短发送输出路径，但仲裁仍需用于计算下一拍的槽号。最长路径可能转移到下一槽号寄存器的反馈路径，不能仅凭输出路径变短就断定整个模块最高频率更高。

若要保持连续每拍一笔发送，下一候选计算必须排除本拍已握手的槽，并正确处理本拍push产生的新候选及其他状态变化。简单增加一级槽号寄存器，可能让首次发送晚一拍，或在连续请求之间插入气泡。时序、启动延迟和吞吐率需要一起比较；“输出路径短”不自动等于整体更优。

### 功耗暂时不能排序

方案 B 减少少量寄存器时钟负载；方案 C 将仲裁与输出选择隔开，可能减少内部变化向宽数据选择网络传播。实际功耗还取决于候选逻辑是否继续翻转、门控方式、背压比例、数据活动率以及综合映射。当前没有足够证据给三种方案排出确定的功耗顺序。

### 后续怎样决定

当前保留方案 A，不因为这次讨论切换实现。若后续要做 PPA 优化，可按下面的目标选择候选方案：

- 面积优先，并希望保持现有启动延迟与吞吐：优先评估方案 B。
- 发送仲裁到数据输出确实是关键路径：优先评估方案 C。
- 现有面积和时序已满足目标：继续使用已通过回归的方案 A 也合理。

实际比较时，应使用相同工艺库、综合与时序约束、输入活动条件，检查面积、关键路径、功耗以及首次发送延迟和连续发送吞吐，再决定是否值得切换。替代实现还需用现有 UVM 环境重新验证，当前的 26 组通过结果仅属于方案 A。

另需注意，[验证计划 WBS-007](../../验证计划/DCacheWithMshr/WBB_IP验证.md)描述了“从 rrPtr 起选第一个候选，仅发送握手更新指针”。方案 B 会改变这一内部更新约定；若以后采用它，应同步说明指针的新职责、参考模型和相关内部检查，保持外部协议及保持性断言不变。本次不修改这些文件。
