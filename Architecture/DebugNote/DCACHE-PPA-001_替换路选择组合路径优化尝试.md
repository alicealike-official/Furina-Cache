# DCACHE-PPA-001 替换路选择组合路径优化尝试

日期：2026-11-26。状态：实验完成，综合及时序未改善，已决定恢复原实现；不保留该实验作为正式优化。按用户要求，本轮不运行功能验证。

## 为什么尝试这个改动

700 MHz 基线为 `synthesis/dcache28/work/run_20261126_084413`：SS 0.81 V、125°C 的最差 setup 裕量为 −0.1123 ns，TT 为 +0.2783 ns。最差路径从 s1Index[3] 到 UnitCache.rdValidPipe_0，包含 29 级组合单元，其中 8 级缓冲合计约 0.2901 ns。标准单元面积为 636430.536 µm²。

门级路径中出现 policy_order 的读取和选择。结合源码，Stage2 先选替换路，判断脏行和资源，再决定是否冻结；冻结结果又控制 R1 地址与使能，最后进入 Cache 读状态寄存器。替换路选择的多次串行选择是本轮优化目标，不宣称它是所有违例的唯一来源。

修改前本地 RTL 与基线 RTL 的 diff 仅有 Git hash 注释，无行为代码差异，因此使用该基线作对照。未修改约束、工艺库或综合流程。

## 改了什么

修改 [ReplacePolicy.scala](../../Design/DCacheMSHR/src/main/scala/furina/dcache/ReplacePolicy.scala) 的 OrderedPolicy.allocWay，FIFO 与 LRU 共用此方法；本轮默认顶层生成 FIFO。PLRU 不受此处修改影响。

原路径是“检查各优先级位置是否可用 → 编码首个可用位置 k → 用 k 再索引 order 得到路号”。新路径是“各位置产生是否为首个可用位置的单一选中信号 → 选中位置的路号保留，其余位置置零 → 按位或合并路号”。这样尝试省去位置编码后再次动态选择路号的串行结构。

例如顺序为 [2,0,3,1]、可用位置为 [0,1,1,0]，新结构选中信号为 [0,1,0,0]，输出仍是路0。全锁时令第0位置选中，保留旧编码器 k 默认0时返回队首的行为；顶层仍按原条件禁止无可用路时分配。没有增加流水寄存器，没有改变替换顺序维护、锁条件、优先空路规则或接口拍数。

这些是源码层面的行为分析，不是功能等价验证结果。用户明确要求先综合，因此本轮不跑仿真、测试或形式验证，也不访问验证文件夹。

## 比较方法及范围

使用现有 run.py，以相同 SS 标准单元库重新映射 700 MHz，再对同一网表进行 TT/SS STA，保留 50 ps 时钟不确定度、200 ps IO 延迟等原约束。重新综合，不复用旧映射网表。

当前仍是存储全部映射标准单元、无 SRAM 宏、无布局布线寄生、理想时钟的评估；不等同于物理实现签核。目标比较 WNS、TNS、标准单元面积和最差路径的寄存器端点及逻辑级数。

原实现最差路径为 s1Index[3] → UnitCache.rdValidPipe_0，新实现仍为同类路径 s1Index[3] → UnitCache.rdValidPipe_1。新路径数据到达时间 1.4722 ns，允许到达 1.3569 ns；SS 仍不满足700 MHz。流程退出码2表示时序未满足，不是映射工具失败。

结论：这次源码层面省掉“位置编码后再索引”的写法，没有转化为更好的映射结果。缓冲级数和最差路径组合级数反而增加；具体各门变化由重新映射决定，不能据此断言 one-hot 方法在所有配置和工具下都更差，也不能把本轮路径差异归结为单个门。
