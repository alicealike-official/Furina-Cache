## 0. 文档说明与阅读指南

本文档描述一个面向处理器的、带缺失状态保持寄存器（MSHR, Miss Status Holding Register）与写回缓冲（WBB, WriteBackBuffer）的**非阻塞数据 Cache**。所谓"非阻塞"，指的是当一条访问请求未命中 Cache 时，Cache 不会停住整个流水线死等内存，而是把该请求登记进 MSHR 后放行后续请求，从而允许在未命中未完成时继续处理其他命中请求（即 hit-under-miss）。

本文面向需要理解、评审或实现该模块的工程人员。全文遵循如下约定：所有接口均为基于 **valid/ready 握手**的流式接口，一次握手定义为 `valid && ready` 同时为高的那一拍；文中以"拍/周期"表示一个时钟周期；所有寄存器默认复位值为 0，所有状态机默认复位到空闲状态，除个别显式声明外不再赘述。文中用【待解决】标记尚未最终确定、留待后续补充的内容。

需要强调的是，本设计定位为**架构学习与自研实践**，因此刻意采用"从简"原则：不实现异常处理、总线错误上报、超时机制、ECC、多核一致性协议、可缓存属性、原子操作以及非对齐/字节级访问。这些不在本文档范围内，也不影响主体数据通路与控制流程的正确性。

与初版相比，本版特别补充了以下此前未闭合或存在歧义的内容：MSHR 的 SEND 发送状态与发送仲裁、命中路径的 Stage2 冻结（Stall）机制、级流水之间的原子性边界、WBB 槽位预留（reserve）机制、写回缓冲与填充顺序保证的窗口处理、`wayLocked` 参与命中判断的规则与副作用、双读双写端口模型及其备选仲裁表、以及替换策略的 onHit/onFill 契约。这些内容在初版中缺失或不完整，是本次修订的重点。

## 1. 引言

### 1.1 设计目的

现代处理器与主存之间存在巨大的速度鸿沟，如果每次访存都直接访问内存，流水线将被严重拖慢。Cache 的作用正是利用程序访存的**时间局部性**与**空间局部性**，把经常访问的数据放在离 CPU 更近、访问更快的小容量存储中。

然而，一个只会"命中就快、未命中就等"的阻塞式 Cache 会在未命中时让 CPU 完全停顿。为了兼顾正确性与吞吐，本设计引入两个关键部件：MSHR 用于**记录并合并正在进行的未命中请求**，WriteBackBuffer 用于**把被替换的脏数据行异步写回内存**。二者共同使 Cache 在未命中期间仍能服务其他请求。

### 1.2 设计范围

本设计覆盖：Cache 的存储体组织、地址映射、读/写命中路径、未命中处理、MSHR 的合并、发送、填充与重放、脏行写回与写回缓冲预留、响应返回与排队、两级流水之间的原子性与 Stall、反压与端口仲裁、可配置替换策略及其与 Way Lock 的联动，以及相关的时序与不变量。

### 1.3 设计目标

第一，**可参数化**：组数、路数、块大小、字宽、MSHR 条目数、总线宽度等均可配置，便于在不同面积/性能目标间权衡。第二，**非阻塞且支持未命中合并**：同一 Cache 行上的多个未命中请求可合并进同一个 MSHR 条目，避免对内存的重复访问，并提高内存级并行度（MLP）。第三，**行为确定、可预测**：命中读固定内部延迟、命中写固定内部延迟，所有边界条件（缓冲满、条目满、同地址冲突、端口冲突）都有明确的 Stall 与反压规则。第四，**不死锁**：整个反压依赖图无环，所有 Stall 都能在有限时间内解除。

### 1.4 非目标（暂不实现）

为控制复杂度，本设计明确**不**支持：字节使能与部分字写（因此所有 CPU 访问必须按字对齐、整字读写）；非对齐访问；异常、总线错误与超时上报；ECC；多核 Cache 一致性；可缓存/可写透等内存属性；原子与独占访问。地址对齐由上层系统保证，不属于 Cache 内部职责。这些内容留作后续扩展。

## 2. 总体架构

### 2.1 系统定位与使用场景

本 Cache 位于处理器与外部内存之间，向上通过一组流式接口接收 CPU 的读/写请求并返回响应，向下通过独立的读、写通道访问内存。它假设内存支持多个未完成事务（outstanding）且**可能乱序返回**，因此必须依靠请求 ID 把响应锚定回对应的发起者。

Cache 采用**写回（write-back）+ 写分配（write-allocate）**策略：命中写只改 Cache 并置脏位，不立即写内存；未命中写会先把整行取回（写分配），合并写入后再标记为脏。命中响应与重放响应的返回**允许乱序**（跨不同 Cache 行的响应可能先于更早发出的未命中响应返回），这正是请求 ID 存在的意义。

### 2.2 顶层结构与模块划分

顶层将数据存储、未命中跟踪、写回缓冲、响应排队和替换策略拆分为相互协作的模块。其连接关系如下图所示。

```text
                 +-----------------------------------------------------------+
   CPU           |                        DCache（顶层）                      |
  ------         |                                                           |
  cpu  --------->|   +-----------+    +-------+    +-------+    +----------+  |
  cpuReadResp <--|   | 请求流水线 |<-->| MSHR  |<-->|  WBB  |<-->| Response |  |
  cpuWriteResp<--|   | & 命中判断 |    |       |    |       |    | Queue    |  |
                 |   +-----+-----+    +---+---+    +---+---+    +----------+  |
                 |         |              |            |                      |
                 |         v              v            v                      |
                 |   +-------------------------------------------+           |
                 |   |                CacheMem                   |           |
                 |   |  valid / dirty / tag / data 存储体          |           |
                 |   |  + 替换策略（Policy）                       |           |
                 |   +-------------------------------------------+           |
                 +-----------------------------------------------------------+
                              |                            ^
                              v                            |
                     memReadReq / memWriteReq        memReadResp / memWriteResp
                              |                            |
                              v                            |
                        +----------------------------------------+
                        |              内存 / 总线                 |
                        +----------------------------------------+
```

各模块职责如下：**CacheMem** 保存 tag、valid、dirty 与数据，并按"路"分体以支持并行比较与并行访问，对外提供两个字读/写通道与整行读/写能力；**MSHR** 负责未命中的登记、合并、向内存发起读请求、填充以及重放；**WBB** 负责暂存被替换的脏行并异步写回，并支持在淘汰动作发生前**预留**槽位；**Response Queue** 负责把命中响应与重放响应排队后返回 CPU；**替换策略（Policy）** 为可插拔模块，决定 victim 路的选择。

### 2.3 数据通路

向上，CPU 请求进入流水线后被分解为 tag、index、wordOff；请求信息随流水打拍，同时 CacheMem 开始同步读。在命中判断阶段，各路的 tag 与 valid 并行比较、并叠加 `!wayLocked` 得到命中路；若命中，读请求从对应路的数据体中取出并送往响应，写请求驱动单字写端口修改命中路的数据。若未命中，请求被送往 MSHR，由其发起内存读；数据返回后写入 CacheMem，并通过重放把结果送回 CPU。向下，内存读由 MSHR 发起，内存写由 WBB 发起，两条通道彼此独立。

### 2.4 控制通路

控制通路的核心是**握手、Stall 与反压**。CPU 侧是否被接收由 `cpuReady` 决定；`cpuReady` 是所有"能否容纳本次请求"条件的组合结果。当一条已接收的请求在 Stage2 发现当前无法完成时，进入 **Stage2 冻结（Stall）**：保持流水寄存器、门控所有对外写操作、拉低 `cpuReady`，直到条件解除。响应侧通过 `cpuReadResp` 与 `cpuWriteResp` 两条独立的流返回，并由响应队列平滑突发。内存侧以 ID 作为锚点：读请求 ID 取自 MSHR 条目位次，写请求 ID 取自 WBB 缓冲区位次，二者空间独立、互不干扰。

### 2.5 关键设计决策与权衡

**其一，为何按路分体存储。** 在命中判断时，必须对同一组的所有路并行比较 tag，因此每一路必须能独立、并行地读出自己的 tag/valid/dirty，故这三类存储按路分体。而数据体则按"路 × 字"分体，原因有二：不同路可能同时被读写；更重要的是，填充整行时同一周期的多个字需要同时写入，若数据存在单一窄口存储体中，就无法一拍写完整行。

**其二，为何采用两级流水。** 同步读存储体天然有一拍读延迟：地址在时钟沿被采样，数据在下一拍才有效。因此设计把"接收并发出地址"和"命中判断并取数"分成两级，用流水换取时序收敛。命中读因此为两拍；命中写比读多一拍，因为写必须先知道命中哪一路才能驱动写端口。

**其三，为何把 Cache 命中排除在 `cpuReady` 之外。** 因为 Cache 是否命中要等到下一拍才知道，而 `cpuReady` 必须在当拍决定是否接收请求。若把命中纳入反压，会引入跨拍的组合依赖，既违和又拖慢关键路径。权衡之下，`cpuReady` 采用"保守反压"：即使请求其实会命中，只要 MSHR 暂时容不下也会被挡一拍。工程上这牺牲了少量性能，换来了清晰、无环的握手时序；相位不一致的残留情形由 Stage2 Stall 兜底。

**其四，为何需要响应队列。** 命中路径和重放路径都可能产生 CPU 响应。如果没有缓冲，当 CPU 一时无法接收响应时，响应就会丢失。响应队列把"产生响应"与"取走响应"解耦，并在队列满时冻结 Stage2 并反压 `cpuReady`，从而保证既不丢响应、也不会无界积压。

**其五，为何需要 SEND 状态与发送仲裁。** 未命中条目的内存读请求可能因总线繁忙而无法立即发出。若把"分配条目"与"发出请求"强行绑在同一拍，就会在总线忙时无法表达"已分配但未发送"。因此引入独立的 SEND 状态，把分配与发送解耦，并用仲裁器在多个待发条目间选择。

为保证地址分解、组相联与位域切分成立，参数必须满足：块大小是字大小的整数倍；组数是 2 的幂；块大小是 2 的幂；字大小（字节数）是 2 的幂；MSHR 条目数是 2 的幂；WBB 条目数也是 2 的幂，且不超过总线最大未完成数。

### 3.4 当前配置说明

当前采用 32 组、4 路、64 字节块，故整个 Cache 容量为 32 × 4 × 64 = 8192 字节，共 8KB。每行 16 个字；tag 21 位，index 5 位，offset 6 位（其中 wordOff 4 位、字节偏移 2 位）。MSHR 可同时跟踪 4 个未命中行，每行最多合并 4 个待处理请求，理论上最多挂起 16 个 CPU 请求，这也正是 CPU 请求 ID 位宽至少需要 4 位的原因。

## 4. 接口与协议

### 4.1 CPU 侧接口

向上有三条流：请求流 `cpu`、读响应流 `cpuReadResp`、写响应流 `cpuWriteResp`。请求流由 CPU 发起、Cache 接收，因此对 Cache 而言是输入（从端）。读响应与写响应由 Cache 发起、CPU 接收，因此是输出（主端）。请求载荷包含：地址（字节地址、字对齐）、读写指示（1 表示写、0 表示读）、写数据（单字宽度）、以及请求 ID。读响应载荷包含读数据与请求 ID；写响应载荷只包含请求 ID。

请求的读写由同一个 `wrEn` 字段区分。写数据仅在写请求时有效；读请求不需要写数据。由于本设计不支持字节使能，写数据始终对应一个完整字。

### 4.2 内存侧接口

向下有四条流，读写各成一对。Cache 作为主端发出 `memReadReq`（地址 + 读 ID）与 `memWriteReq`（地址 + 整行写数据 + 写 ID）；作为从端接收 `memReadResp`（整行读数据 + 读 ID）与 `memWriteResp`（写 ID）。内存地址是字节地址但要求**块对齐**，即低 offsetWidth 位恒为 0；读数据与写数据都是整个 Cache 行的宽度（wordsPerBlock × DATA_WIDTH）。

读写通道相互独立，因此读 ID 与写 ID 属于两个独立的 ID 空间，可以同时存在、互不影响。内存支持多个未完成事务并可能乱序返回，故所有响应都以各自通道的 ID 作为锚点回填。内存每拍最多返回一个读响应和一个写响应，但读、写可以同拍各响应一个；这一约定是 MSHR 填充与 WBB 写回时序的前提。

### 4.3 地址语义与对齐

CPU 地址是字节地址，但要求按字对齐；内存地址是字节地址，但要求按块对齐。之所以统一用字节地址表达，是为了与常见总线约定一致；之所以强调对齐，是因为本设计不支持字节级访问，若允许非对齐地址，就无法确定一次访问究竟落到哪个字。对齐约束由上层系统保证，Cache 不对非对齐地址定义行为。

### 4.4 数据语义

每次 CPU 读返回一个完整字；每次 CPU 写写入一个完整字。因为不支持字节使能，写命中只影响目标字所在的那一路的那一个数据体条目，同行的其余字保持不变。填充（Fill）时则以整行为单位写入所有字，因此要求内存读响应一次性返回整行数据。

### 4.5 ID 语义与位宽匹配

CPU 请求 ID 由外部提供，Cache 只做透传：命中读直接把请求 ID 放进读响应，命中写直接把请求 ID 放进写响应，重放时则使用当时记录在 Slot 中的响应 ID。内部各 ID 的位宽含义需要区分清楚：MSHR 条目位次宽度为 mshrIdWidth，WBB 缓冲区位次宽度为 wbbIdWidth，而内存读写接口上的 ID 位宽为 busIdWidth。由于 busIdWidth 通常大于 mshrIdWidth/wbbIdWidth，向内存发请求时必须把条目位次**零扩展**到总线 ID 宽度；接收响应时则取总线 ID 的低若干位去索引条目，并校验高位为 0（高位非 0 属于【待解决】的异常场景，本设计暂不处理）。这一位宽映射必须在文档与实现中保持一致，否则会出现索引错位。

### 4.6 握手与反压

所有流均遵循标准 valid/ready 语义：发送方拉高 valid 并保持载荷稳定，直到接收方拉高 ready 且完成握手；一次握手后载荷才可改变。反压时，发送方的 valid 必须保持、载荷必须保持，不得撤回请求。这一语义与常见总线的 valid/ready 契约一致，因此该 Cache 可以直接与符合该契约的 CPU 和内存模型对接。

## 5. 地址映射与 CacheMem 组织

### 5.1 地址分解

对于 CPU 请求地址，自高到低划分为 tag、index、offset 三段：tag 用于与各路的 tag 比较以判断命中；index 用于选择组（set）；offset 表示块内偏移。offset 内部又分为高位的 wordOff（块内第几个字）与低位的字节偏移。由于要求字对齐，最低的字节偏移位恒为 0，因此 wordOff 等价于取 offset 的高位。内存请求地址取 CPU 地址去掉低 offsetWidth 位，得到块对齐的字节地址。

```text
 31                21 20        6 5          2 1   0
+--------------------+-----------+------------+-----+
|        tag         |   index   |  wordOff   |byte |
+--------------------+-----------+------------+-----+
        21 位            5 位         4 位      2 位

   内存地址 = CPU 地址去掉低 6 位（offsetWidth）
```

### 5.2 存储体划分及原因

有效位（valid）、脏位（dirty）与 tag 三者按**路**分体：每一路各有自己的 valid/dirty/tag 存储体，体内按 set 索引。这样在命中判断时，同一个 set 的所有路可以并行读出各自的 tag 与 valid 并同时比较，得到 wayHits 向量，进而得到命中与否以及命中路。数据体则按**路 × 字**分体：每一路的每一个字各占一个独立存储体，体内按 set 索引。

```text
  valid / dirty / tag：按路分体            data：按 路 × 字 分体

      way0        way1                           word0    word1   word2  ...
    +--------+  +--------+                  way0 +------+ +------+ +------+
    | set0   |  | set0   |                       |bank00| |bank01| |bank02|
    | set1   |  | set1   |                  way1 +------+ +------+ +------+
    | set2   |  | set2   |                  way2 +------+ +------+ +------+
    |  ...   |  |  ...   |                  way3 +------+ +------+ +------+
    +--------+  +--------+                        （每个 bank 深度 = NUM_SETS）
```

如此划分的直接收益是：命中比较可以并行；填充整行时，由于每一路的每个字都有独立存储体，可以在一拍内把整行 16 个字同时写入。

### 5.3 读端口

本设计对外提供**两个字读通道**：

- **读通道 R1（流水线字读）**：用于命中判断。它按 index 读出同一组所有路的 tag、valid、dirty，并按 wordOff 读出每一路的那个字。每个 CPU 请求都需要它，属于关键路径。
- **读通道 R2（victim 整行读）**：用于把被替换的 victim 行整行取出、送往 WBB。它以 victim 的 set 与 way 为地址，一次并行读出该路下的全部 wordsPerBlock 个字，拼成一整行（当前配置为 512 位）。它只在未命中且 victim 为脏时发生。

两个读通道可同拍各自工作；由于每个存储体是真双端口（见 5.5），同一拍对同一个 bank 的两次读不会冲突。

### 5.4 写端口

本设计对外提供**两个写通道**，另有独立的清零通路。写操作分三类：

第一类是**填充写**：当 MSHR 从内存取回整行、准备写入 Cache 时使用。它写入组号、路号、tag，把 valid 置 1，把 dirty 置为"该行是否有写请求"的结果，并把整行数据一次写入所有字。该类写走写通道 W2。

第二类是**命中单字写**：当 CPU 写请求命中时使用。它只写入目标字所在的存储体，命中路的其余字保持不变，同时把该行的 dirty 置 1。为了只写一个字，写端口必须携带目标字偏移，并只对目标字所在体使能写。该类写走写通道 W1。

第三类是**替换清零**：当某行被选作 victim 且（若为脏）其数据已成功送入 WBB 之后，用它把被替换行的 valid 清零。清零只写有效位存储体，不写数据体，也不清 dirty（dirty 留待后续填充时覆写，功能上无影响）。清零走独立的有效位写通路，与数据体的读写互不相干。

清零与写回缓冲的关系至关重要：**必须先确认脏数据已成功进入 WBB（或 WBB 槽位已成功预留），才能清除该行的 valid**，否则会丢数据。

### 5.5 端口访问规则与仲裁

本设计的端口模型为"2 读 + 2 写"，且**每个存储体为真双端口（TDP）**：每个 bank 的两个端口均可独立进行读或写。由此可以证明：同一拍内，任一 bank 最多被访问两次（或两次读、或两次写、或一读一写），恰好落在两个端口上。因此**正常情况下不存在同 bank 端口冲突，无需在同 bank 上再做仲裁**。

| 通道 | 用途 | 优先级/说明 |
| --- | --- | --- |
| 读通道 R1 | 流水线字读 | 每个请求都要用，关键路径，不能被抢占 |
| 读通道 R2 | victim 整行读 | 仅在未命中且 victim 为脏时发生 |
| 写通道 W1 | 命中单字写 | 可顺延一拍，由 Stage2 Stall 保持请求 |
| 写通道 W2 | 填充整行写 | 未命中关键路径，延迟它会反压内存，优先级高于 W1 |
| 清零通路 | victim 清 valid | 只写有效位存储体，与数据体读写不冲突 |

关于 W1 与 W2：当命中写（W1）与填充写（W2）同拍、且恰好落在同一个 bank 时，**W2 优先，W1 顺延到下一拍**，并由 Stage2 Stall 保持该写请求不丢。在 TDP 存储体下该情形不会出现，此规则仅作为最坏情况的兜底；若后续因面积/功耗改用单端口或 1R1W 的低成本存储体，可启用附录 15.2 的备选仲裁表。

### 5.6 复位与初始化

复位时，所有 valid 与 dirty 清零，所有 tag 与 data 清零，替换策略状态复位（见第 10 章），MSHR 状态机回到空闲，WBB 视为空，响应队列清空。

## 6. CPU 请求流水线

### 6.1 流水线阶段划分

请求处理分为两级。 **Stage1（接收与发地址）** 在同一拍完成握手、地址分解、驱动 CacheMem 读端口，并并行执行一组"是否可接收"的检查。 **Stage2（命中判断与执行）** 使用 Stage1 打拍锁存下来的请求信息，比较各路 tag 得出命中与否，并据此执行命中读、命中写，或未命中处理。

### 6.2 Stage1：接收、地址分解与并行检查

Stage1 中，地址立即被分解为 tag、index、wordOff、blockAddr 等字段。index 与 wordOff 驱动 CacheMem 的读通道 R1，读使能取决于本拍是否成功握手（或是否处于 Stage2 Stall）。与此同时，以下检查**并行且相互独立**地执行，共同决定 `cpuReady`：

| 检查项 | 目的 | 对 cpuReady 的影响 |
| --- | --- | --- |
| Cache tag 读 | 为 Stage2 命中判断做准备 | 不反压 |
| MSHR 命中检查 | 判断能否合并进已有条目 | 命中但不可合并 → 反压 |
| MSHR 空闲检查 | 判断未命中时能否分配新条目 | 未命中且无空条目 → 反压 |
| 可用 way 检查 | 判断未命中时是否有可替换的路 | 无可用 way → 反压 |
| WBB 满检查 | 能否容纳可能产生的脏行写回 | 满 → 反压（保守） |
| WBB 同地址检查 | 防止写回与填充的先后顺序被破坏 | 同地址 → 反压 |
| 响应队列满检查 | 防止响应无处安放而丢失 | 满 → 反压 |

这些检查之所以能并行，是因为它们各自只依赖当拍输入与当前状态，彼此无先后依赖。需要特别指出：**MSHR 匹配的"估计"在 Stage1 完成，但"是否接收、如何提交"是 Stage1 与 Stage2 的综合结果**——因为 MSHR 状态可能在这两拍之间改变（例如某条目恰好在本拍收到内存响应而进入填充），而新分配的条目要到下一拍才可见。因此 Stage1 的 MSHR 匹配只是估计，Stage2 会重新判定并提交，具体见 6.8 与第 7 章。

### 6.3 Stage2：命中判断与执行

Stage2 将锁存的 tag 与各路读出的 tag 并行比较，且要求该路 valid 有效、**且该路未被 Way Lock 锁定**，得到 wayHits。只要任一路命中即为命中，并给出命中路。

> **命中判断的基础规则：** 某路的命中条件为该路 valid 有效、tag 匹配、且 `!wayLocked(该 set, 该路)`。`wayLocked` 参与命中判断，是为了让正在被淘汰或正在被 MSHR 填充/重放的路对命中判断不可见（其副作用见 10.4 与 13 章）。

随后根据请求类型分派：

若 Cache 命中且为读，则从命中路数据体中取出对应字送往读响应；若 Cache 命中且为写，则驱动单字写端口，并在本拍产生写响应。

若 Cache 未命中，则进入 MSHR 处理：若该行已有 MSHR 条目且可合并，则把请求并入对应条目的一个 Slot；否则分配一个新的 MSHR 条目，并在同拍选出 victim 路（若 victim 为脏，则按第 8 章进行 WBB 预留）。

### 6.4 命中读流程与时序

命中读共两拍。第一拍：CPU 拉高 valid，`cpuReady` 决定是否接收；握手成功后地址分解、发出读地址、请求信息打拍暂存。第二拍：各路 tag/valid 并行读出并叠加 `!wayLocked` 比较得到命中路，同拍从命中路数据中选出目标字，推入读响应队列。这里的"两拍"是**内部产生延迟**；从 CPU 端观察到的延迟还会叠加响应队列排队与反压，因此并非恒定两拍。

### 6.5 命中写流程与时序

命中写共三拍。第一拍与读相同（接收、分解、发读地址——即便写也必须先读 tag 才能知道命中哪一路）。第二拍：比较得到命中路，驱动单字写端口，并在本拍返回写响应。第三拍：写入在第二到第三拍的时钟沿真正生效。因此从 CPU 角度看，写请求在第一拍发出、第二拍收到写响应；从存储体角度看，写入在第三拍生效。写响应的语义是"请求已被接受"，不保证存储体已经更新完毕。

### 6.6 写后读冒险与旁路

由于写要到第三拍才生效，而读可以在第二拍就取数，存在一个一拍的冒险窗口：当一个写请求正在把数据驱动到写端口时，同拍恰好有一个读请求要访问相同的"组 + 路 + 字"，则读在下一拍取数时会与写入在同一时钟沿竞争；究竟读到新值还是旧值，取决于存储体自身的读写优先结构。为消除这种不确定性，本设计**统一采用旁路**：在读数据输出路径上增加选择，当检测到"写请求的目标（组 + 路 + 字偏移）"与"读请求的目标"完全一致、且写使能有效时，直接用写数据替代从存储体读出的数据。

```text
   rdData(hitWay) ----+
                      +----> [MUX] ----> cpuReadResp.rData
   wrWordData --------+                 ^
                                        |
                                  conflictHit
```

由于任何情况下都直接采用写数据，无论存储体是读优先还是写优先，结果都一致，从而消除了实现不确定性。

需要区分的是，这里讲的是 **CPU 流水线内部的写后读旁路**；MSHR 重放时的"填充数据 + 前序写"合并是另一条独立通路，见 7.11。

### 6.7 命中路径的优先级

命中的请求优先于 MSHR 的重放请求。当命中请求在本拍产生响应时，会反压（暂停）MSHR 的重放，从而保证同一响应类型在同一周期最多只有一条响应产生。注意：读响应与写响应分属两条不同的响应队列，因此"命中优先"是在**同一响应类型内部**生效；一条命中读与一条重放写可以在同一拍各自推入各自的队列。

### 6.8 Stage2 冻结（Stall）

Stage1 的 `cpuReady` 是"估计"，而 Stage2 才是权威提交点。由于 MSHR/方式等状态可能在 Stage1→Stage2 之间改变，某条请求虽已被接收，却可能在 Stage2 发现当前无法处理。此时进入 **Stage2 冻结**：

- 保持 Stage2 的全部流水寄存器（请求信息）不推进；
- 门控 Stage2 的一切对外写操作：不驱动 MSHR 写、不驱动 CacheMem 写、不向响应队列推入；
- 通知 Stage1：`cpuReady = False`，从而反压后续请求；
- 冻结期间仍**保持 Mem 的读地址与读使能**（读使能 = `fire || s2Stall`，地址恒为当前请求的 index），使同步读对同一地址持续重采、数据滚动刷新；
- 待冻结条件消失后，恢复正常处理并继续接收新请求。

冻结条件的精确形式见 11.2。冻结期间保持读刷新，是为了保证解除冻结后 Stage2 使用的是**最新**的 tag/valid，避免用陈旧快照重试而误判。

## 7. MSHR

### 7.1 作用

MSHR 是未命中处理的枢纽。它把一条 Cache 行上的未完成访问集中管理：登记未命中、合并同行的后续请求、向内存发起整行读、等数据返回后填入 Cache，最后按原始顺序把每个请求的结果重放给 CPU。由于同一行只发一次内存读，MSHR 既省带宽又提高了并行度。

### 7.2 Entry 与 Slot 结构

MSHR 由若干 Entry 组成，每个 Entry 对应一条正在处理的 Cache 行；Entry 内又由若干 Slot 组成，每个 Slot 对应一个待处理的 CPU 请求。

Entry 的主要字段如下：

| 字段 | 含义 |
| --- | --- |
| valid | 该条目是否有效 |
| tag / index | 该行在 Cache 中的标识（命中判断/填充用） |
| allocWay | 为该行分配的 Cache 路 |
| fillData | 从内存返回的原始整行数据 |
| pendingSlots | 挂起的请求槽位数组 |
| state | 条目状态：IDLE（空闲）/ SEND（已分配待发送）/ MISS_WAIT（已发送待响应）/ FILL（填充与重放中） |
| replayCnt | 当前重放到第几个 Slot |
| validCnt | 本条目共有多少个需要重放的 Slot |
| hasWriteSlot | 本条目是否含写请求（决定填充时的 dirty） |
| wbSlotIdx | 本条目对应的、已预留的 WBB 槽位下标（仅在 victim 为脏时有效） |

Slot 的主要字段如下：

| 字段 | 含义 |
| --- | --- |
| valid | 该槽位是否有效 |
| isWrite | 该请求是读还是写 |
| wData | 写数据 |
| wordOff | 请求在行内的字偏移 |
| respID | 返回给 CPU 时使用的请求 ID |

注意：MSHR 条目不区分"读条目/写条目"，读写只由 Slot 记录。因此同一行上的读与写可以合并进同一条目。此外，多个 MSHR 条目可以指向不同的行并行处理，从而提高内存级并行度。

### 7.3 状态机

每个 Entry 维护一个独立状态机，在四个状态间迁移：IDLE（空闲，等待分配）、SEND（已分配，正尝试把读请求送上总线）、MISS_WAIT（读请求已被总线接受，等待内存响应）、FILL（内存数据已到，正在填充与重放）。迁移关系为：

- IDLE 在被分配时转入 SEND；
- SEND 在"本条目的读请求被总线接受（握手成功）"时转入 MISS_WAIT；
- MISS_WAIT 在收到对应内存响应时转入 FILL；
- FILL 在完成所有 Slot 重放后回到 IDLE，并统一清除条目与所有 Slot 的有效位。

```text
          分配条目              总线接受              内存响应
  IDLE ------------> SEND ----------------> MISS_WAIT --------> FILL
    ^                                                            |
    |                    重放完成                                 |
    +------------------------------------------------------------+
```

采用独立的 SEND 状态，是为了把"分配条目"与"发出请求"解耦：条目在总线繁忙时可以停留在 SEND 等待发送，而不会因为没有独立状态而无法表达"已分配但未发送"。需要特别说明：**SEND 与 MISS_WAIT 均可接收同地址合并**，因此合并判定必须同时覆盖这两个状态（见 7.4）。

### 7.4 命中判定

MSHR 命中判定为：某 Entry 有效，且其 tag、index 与当前请求完全一致。命中之后还要看状态：**处于 SEND 或 MISS_WAIT 的条目可以接收合并**；处于 FILL（含重放）的条目不接收合并；IDLE 表示条目空闲、尚未分配，不参与命中。

需要区分"匹配"与"接收"：

- **MSHR 匹配（Stage1 估计）**：Stage1 用当前地址与 MSHR 当前条目寄存器比较，得出"是否命中某条目"以及"该条目能否合并"。这只是一个估计，因为 MSHR 状态可能在 Stage1→Stage2 之间改变。
- **MSHR 提交（Stage2 权威）**：Stage2 用打拍后的请求重新判定匹配与可合并性，并据此真正写入 Slot 或分配新条目。若此时发现条目已进入 FILL（不可合并），则不提交，进入 Stage2 冻结等待。

因此，"MSHR 命中"并不等于"请求会被接收"；最终接收/提交是 Stage1 与 Stage2 的综合结果。

### 7.5 合并与分配规则

| 情形 | 条件 | 行为 |
| --- | --- | --- |
| 命中且可合并 | 命中 MSHR 且条目处于 SEND 或 MISS_WAIT，且 Slot 未满 | 合并进该条目 |
| 命中且不可合并 | 命中 MSHR 但条目处于 FILL，或 Slot 已满 | 反压/Stage2 冻结 |
| 未命中且资源可用 | 未命中 MSHR，且有空条目、有可用 way、WBB 可用 | 分配新条目 |
| 未命中且资源不足 | 未命中 MSHR，但无空条目/无可用 way/WBB 冲突 | 反压 `cpuReady` |

条目是否满（有无空条目）与 Slot 是否满，均在 Stage1 用**并行组合逻辑**判定。因为 CPU 每拍最多发一个请求，不存在"同一拍多个请求争抢同一槽位"的排序问题。

### 7.6 Slot 排序

先到的请求占据更低的槽位下标，因此槽位下标天然反映请求到达顺序（也即程序顺序）。重放时按槽位下标从低到高依次处理，保证同一行上的多个请求按原始顺序返回。这一"到达顺序即程序顺序"的前提是：CPU 每周期最多发出一个访存请求。

### 7.7 向内存发起读请求

新条目在 Stage2 被分配后立即进入 SEND 状态，并尝试把整行读请求送上内存读通道。由于总线可能繁忙，发送与分配解耦：

- 多个处于 SEND 的条目可能同时想发送，需要一个**发送仲裁器**。本设计采用简单的**低位下标优先**（即优先级编码），因为 MSHR 规模小、发送频率低，暂时不担心饥饿；若后续扩展 MSHR 条数，可改为轮询。
- 被选中的请求一旦驱动到总线上，**其结果必须锁存到被总线接受为止**（不可抢占）：即无论仲裁器如何在多个待发条目间选择，正在占用总线的那个请求的载荷不能改变，直到握手完成。这由发送仲裁器输出到总线之间的保持寄存器保证。
- 条目"属于本条目且握手成功"是转入 MISS_WAIT 的唯一条件；由于多个 SEND 条目可能同拍存在，该条件必须带"本条目即被选中者"的限定，否则会出现"未被选中的条目误以为已发送"而丢失请求。
- 若总线持续繁忙，条目停留在 SEND；这不直接反压 `cpuReady`。只有当条目因长期发不出去而被 Slot 填满时，才可能间接导致 `cpuReady` 拉低。
- 内存读请求的地址为该行的块对齐地址，ID 取该条目的位次并零扩展到总线 ID 宽度。

### 7.8 内存响应与填充

内存读响应携带 ID，用其低位索引回对应条目，并把整行原始数据存入 `fillData`。由于内存每拍最多返回一个读响应，因此每拍最多只有一个条目需要填充，无需为"填充写 Cache"设置仲裁。收到响应的条目由 MISS_WAIT 转入 FILL。

### 7.9 mergedData 合并规则

填充进 Cache 的数据并非 `fillData` 原样，而是把条目内所有写 Slot 的数据按 wordOff 覆盖到 `fillData` 上得到的"合并数据"。由于本设计只支持整字写，合并是**以字为单位覆盖**，不存在字节级掩码。可以有多个写 Slot 落在同一个字上，此时按到达顺序后者覆盖前者，最终写入 Cache 的是最后一个写值。

### 7.10 Fill 的 dirty 规则

填充时该行是否置脏，取决于本条目内是否存在写请求，即"填充且存在写 Slot"才置脏；若本条目全是读请求，则填充后该行是干净的。不能用"是否填充"直接当作 dirty，否则纯读未命中也会错误地把行标脏。

### 7.11 Replay

Replay 是 MSHR 把挂起请求逐个还给 CPU 的阶段，发生在 FILL 状态。进入 FILL 的第一拍先把合并数据写入 Cache（走写通道 W2）；从之后每一拍处理一个 Slot。

对读 Slot，返回的数据来自"`fillData` + 该 Slot 之前的同字写"的合并视图，而**不是**去读 Cache：因为此时 Cache 中已是所有写合并后的最终值，若直接读 Cache，读请求就会看到位于它之后的写在程序语义上"穿越"过来的值，违背顺序。为此在条目内部做旁路：当某读 Slot 之前存在有效的、写同一 wordOff 的 Slot 时，用最近的那个写数据替代 `fillData` 对应字。对写 Slot，只需返回写响应（其写数据早已在填充时合并进 Cache），不再重复写 Cache。

```text
  FILL 第 1 拍：把合并数据写入 Cache（写通道 W2）
        |
        v
  重放 slot[0] -> 重放 slot[1] -> ... -> 重放 slot[n-1]
        |
        v
  清除条目 valid 与所有 slot valid，回到 IDLE
```

### 7.12 多 Entry Replay 轮询

重放可能持续多拍，因此同一时刻可能有多个条目都处于 FILL 且都等待重放。为避免它们争抢响应端口，需要一个**条目级**轮询仲裁器：每拍只选中一个处于重放状态的条目，处理它当前的那一个 Slot。注意这里的"轮询"指的是**多个条目之间的轮询**，而不是一个条目内部多个 Slot 的轮询——条目内部的 Slot 永远按下标从低到高顺序处理。轮询指针在每次成功处理一个 Slot 后前移，形成公平调度、避免高位条目饥饿。新进入 FILL 的条目同样纳入轮询。填充写 Cache 本身不参与该轮询，因为每拍只有一个内存响应、只有一个条目需要填充。

### 7.13 条目释放

条目在其所有 Slot 都重放完毕后释放：当重放计数到达"有效槽位数减一"（即正处理最后一个 Slot）且该 Slot 完成握手时，清除条目 valid 以及所有 Slot valid，回到 IDLE，并释放对应的 Way Lock（见 10.4）。释放后该条目位次可被后续未命中重用。

### 7.14 与命中路径的关系

对同一个请求而言，Cache 命中判断在 Stage2（且需一拍读）、MSHR 匹配估计在 Stage1（当拍即可），因此请求不会"同时命中 Cache 又命中 MSHR"。更精确地说：当某行存在 MSHR 条目且处于 FILL/重放阶段时，该行的路被 Way Lock 锁住，命中判断因 `!wayLocked` 而不成立；任何针对**同一地址**的新请求会被判为未命中并走 MSHR，此时命中条目但不可合并，于是进入 Stage2 冻结，直到重放结束、方式解锁，该行恢复为可命中的有效行。而针对**其他地址**的请求，只要 MSHR 尚有空条目且该 set 有可用 way，就不受影响。需要强调：这一"不受影响"仅在 MSHR 尚有空条目时成立；若 MSHR 条目全满，则非同地址请求同样会被保守反压。

## 8. WriteBackBuffer

### 8.1 作用

当发生未命中且需要替换一个脏行时，必须先把脏行写回内存，才能让新行占用该路。若让 Cache 停下来等写回完成，会严重拖慢处理。WBB 的作用就是**接管脏行的写回**：把被替换的脏行暂存进缓冲，由缓冲在后台异步写回内存，Cache 本身则可立即继续处理新行的填充。为在"淘汰动作发生的当拍"就保证脏数据有地方安置，WBB 还提供**槽位预留（reserve）**能力。

### 8.2 结构

每个缓冲条目包含：有效位（valid）、预留位（reserved）、写回地址（块对齐）、整行数据、以及"是否已发出写回请求"标志（issued）。缓冲条目的 ID 与它的位次一致，因此无需额外存储 ID。

| 字段 | 含义 |
| --- | --- |
| valid | 该缓冲是否已装载有效数据 |
| reserved | 该槽位已被某个未命中预留、但数据尚未写入 |
| addr | 写回地址（块对齐） |
| data | 整行数据 |
| issued | 是否已向内存发出写回请求 |

### 8.3 状态编码与生命周期

缓冲条目的生命周期为：**预留（写 addr）→ push（写 data、置 valid）→ memWriteResp（释放）**。其中：

- **预留**：在淘汰动作发生的当拍，选出一个空闲槽位并置 `reserved=1`，同时写入 victim 的地址；`valid` 仍为 0。
- **push**：下一拍（victim 整行数据从读通道 R2 返回后），把整行数据写入该槽位，置 `valid=1`、清 `reserved`。此后该槽位的所有权移交 WBB，MSHR 不再干预。
- **释放**：收到内存写响应（`memWriteResp`）握手后，清 `valid`，槽位变为空。ID 不释放——因为 valid 已清零，该条目只需等待下一次覆盖。

槽位的"占用"与"空闲"判定必须**同时计入 `valid` 与 `reserved`**：选择空闲槽时需要跳过 `reserved`，判断"满"时也需要把 `reserved` 计入。否则会出现两个未命中预留到同一槽位（双占）或把已预留的槽位当成空闲。

### 8.4 预留机制

并非所有未命中都需要预留：**只有 victim 为脏行时才需要**（写回缓冲模块本身只为脏行服务，干净行直接放弃、被替换即可）。预留成功与否，决定淘汰动作能否发生：

- 淘汰动作的使能为 `doAllocate && wbReserveSuccess`。
- 预留成功时，才执行"清 victim 的 valid、分配 MSHR 条目、置 Way Lock、读出 victim 整行"这一组动作。
- 预留失败时，**整组动作都不做**：victim 的 valid 保持为 1、脏数据仍留在 Cache 中，请求留在 Stage2 进入冻结，等 WBB 有空位后再重试。

这样设计保证了"要么脏数据被安全安置、要么一切照旧"，不会出现"valid 已清而脏数据无处安放"的丢数据。

### 8.5 替换写回流程与时序

发生未命中需要替换脏行时，时序如下：Stage2 判定未命中并组合选出 victim；同拍组合准备"Way Lock、WBB 预留+写 addr、清 valid、分配 MSHR、读 victim 整行"；在 Stage2 的下一时钟沿，这组动作**原子生效**。之后某一拍整行数据从 R2 返回并 push 进预留槽；再之后某一拍 WBB 轮询选中该槽位、发出内存写请求并置 issued；最终收到内存写响应后槽位释放。

### 8.6 发送仲裁

当同时存在多个"有效且等待发出（valid=1 且 issued=0）"的缓冲条目时，由轮询仲裁器决定每拍发出哪一个，以保证公平、避免低优先级条目被长期饿死。

### 8.7 同地址顺序保证

存在一个隐蔽但重要的风险：被替换脏行的写回可能尚未完成，而针对**同一地址**的新未命中却已经开始从内存读回数据。如果内存先返回了读数据，就会用旧数据覆盖掉尚未写回的新数据，破坏顺序。

解决思路分两层：**其一**，在 MSHR 判定未命中时（以及 Stage2 重查时）检查 WBB 中是否存在同地址的写回请求——检查范围必须覆盖 `valid` 和 `reserved` 两种状态，且预留槽位在预留当拍即写入 addr 以参与匹配。**其二**，由于 Stage1 的检查可能因"预留恰好在同拍建立"而漏掉，Stage2 需要**再查一次**；若冲突，则冻结并等待该写回完成。这样既能做到只反压同地址请求（不同地址照常分配），又能堵住 Stage1→Stage2 的窗口。

### 8.8 满与 reserved 的判定

"WBB 满"定义为"所有槽位均被占用"，即对所有槽位 `valid || reserved` 成立。该信号是 WBB 对外提供的一个独立指示，而不是简单地把某一状态位当成满。WBB 满时，Stage1 即拉低 `cpuReady`。这是保守策略：即使当前请求其实会命中、根本用不到 WBB，也会被一并挡下——代价是少量性能损失，收益是保证"请求一旦被接收，就一定找得到地方安置其可能产生的脏行"。

## 9. Response Queue

### 9.1 必要性

CPU 响应有两个来源：命中路径（Stage2 产生）与 MSHR 重放路径。若让它们直连顶层响应端口，当 CPU 因自身原因暂时无法接收响应时，响应就会丢失；同时两个来源直接对接也会造成多驱动冲突。因此需要响应队列：先把响应压入队列，再由队列按流式协议交给 CPU。

### 9.2 结构

读响应与写响应各用一条独立队列（因为二者数据类型不同）。两条队列的深度均可参数化，当前取 4（深度只是参数示例）。每条队列都是一个先进先出缓冲，**每拍只有一个写口**：命中响应与重放响应都向其推入，队首向 CPU 弹出。

```text
   命中响应 --+
              +--> push --> [ 读响应 FIFO ] --pop--> cpuReadResp
   重放响应 --+                    |
                                   +--> 满 --> 冻结 Stage2 / 反压 cpuReady

   命中响应 --+
              +--> push --> [ 写响应 FIFO ] --pop--> cpuWriteResp
   重放响应 --+                    |
                                   +--> 满 --> 冻结 Stage2 / 反压 cpuReady
```

### 9.3 规则

读、写各一队列；深度参数化；两条队列任一满都冻结 Stage2 并反压 `cpuReady`；在同一队列类型内部，命中响应优先于重放响应推入。由于读、写队列相互独立，一条命中读与一条重放写可以同拍各自推入各自的队列，不互相阻塞。

关键的是：**命中响应在 Stage2 才产生**，而 Stage1 的"队列满"检查是当拍的，两者之间队列可能被上一拍的重放响应填满。因此响应队列满必须纳入 Stage2 的冻结条件（见 11.2），否则命中响应会在 Stage2 无处安放而丢失，恰与响应队列的初衷相悖。若队列满，意味着 CPU 已经积压了足够多的待处理响应、暂时无力再接收新请求，故 Stage1/Stage2 不再接收或提交新请求，直到 CPU 能取走响应为止。

## 10. 替换策略

### 10.1 接口抽象

替换策略被抽象为一个可插拔模块，对外提供三个动作：根据组号选出一个候选替换路（分配时用）、在命中时更新策略状态（onHit）、在填充时更新策略状态（onFill）。Cache 顶层通过工厂在编译期注入具体策略，从而在不改动主体逻辑的前提下切换算法。策略内部通常为每个组维护独立的状态（如指针、顺序队列等）。

### 10.2 候选策略

可配置的候选包括：随机、先进先出（FIFO）、最近最少使用（LRU）、伪最近最少使用（PLRU）。具体微架构留待后续补充。

### 10.3 onHit / onFill 契约

- **onHit**：在 Stage2 命中判定成立的那一拍触发，参数为 `s1Index`（命中的组）与 `hitWay`（命中的路），语义为"该路刚被访问"。命中读与命中写都应触发。
- **onFill**：在填充写 Cache 的那一拍触发，参数为 `index` 与 `allocWay`，语义为"该路刚被填充"。

以上是主数据通路与策略之间的接口契约；策略内部的具体实现细节可后续补充。

### 10.4 victim 选择与 Way Lock

选择 victim 时，首先优先使用该组中"尚无效（空）且未被锁定"的路；若无这样的路，才交由替换策略给出候选，且候选必须跳过被锁定的路。若所有路都被锁、或既无空路又无可替换路，则该请求不可接收。

**Way Lock 的生命周期与 MSHR 条目严格一致**：从 MSHR 分配该条目的那一刻置位（置位对象为该条目的 `allocWay`），一直到条目释放（即重放完成、重放计数到达"有效槽位数减一"的那一拍）才清除。之所以不能在"填充写完成"时提前释放，是因为会引发二次释放 bug：假设条目 0 填充完某路后立即清锁，随后条目 1 可能又选中该路并重新置锁，而当条目 0 真正释放时若再次清锁，就会把条目 1 的锁误清，导致该路在条目 1 仍在使用时被替换策略再次选中，造成数据错乱。因此锁的释放必须与条目的释放一一对应。

```text
   MSHR 分配条目  ──置位──►  WayLock[set][allocWay] = 1
         │
         │（MISS_WAIT / SEND / FILL 全程保持锁定）
         ▼
   条目释放（重放完成）──清除──►  WayLock[set][allocWay] = 0
```

**Way Lock 参与命中判断的副作用（必须写清）：** 由于命中判断要求 `!wayLocked`，在条目从分配到释放的整个生命周期内，其占用的路对命中判断不可见。这意味着：对该行地址的一切请求都会被视为未命中并走 MSHR 路径，其中同地址请求因"条目处于 SEND/MISS_WAIT 可合并"而被合并、或因"条目处于 FILL 不可合并"而进入 Stage2 冻结，直到条目释放后该行才重新可命中。这是"重放期间阻塞同地址请求"这一行为的实现基础，属于有意设计，而非缺陷。

### 10.5 复位值

替换策略的状态在复位时应有确定初值（例如 FIFO/LRU 的顺序队列初始化为 0、1、…、NUM_WAYS−1）；LRU 的具体复位值【待解决】。

## 11. 反压、Stall 与仲裁

### 11.1 cpuReady 的精确条件

`cpuReady` 为高（可接收）当且仅当下面条件成立：

```text
cpuReady =
    !respFifoFull
    && (
         canMerge
         || ( !hitInMshr
              && hasFree
              && !wbFull
              && !wbSameAddr
              && hasAvailableWay )
       )
```

其中：

- `canMerge`：命中某 MSHR 条目，且该条目处于 SEND 或 MISS_WAIT，且对应 Slot 未满；
- `hitInMshr`：当前请求命中某 MSHR 条目（即已存在同地址条目，但可能不可合并）；
- `hasFree`：存在空闲 MSHR 条目；
- `wbFull`：WBB 所有槽位均被占用（valid 或 reserved）；
- `wbSameAddr`：WBB 中存在与当前请求同地址的写回/预留条目；
- `hasAvailableWay`：该请求的 set 下存在至少一个"valid=0 或 `!wayLocked`"的路；
- `respFifoFull`：对应类型的响应队列已满。

需要再次强调，Cache 是否命中**不在**该条件之列；`cpuReady` 采用保守策略，宁可多挡一拍。Stage1 的并行检查只是"估计"，权威提交在 Stage2。

### 11.2 Stage2 冻结的精确条件

当一条已被接收的请求进入 Stage2 后发现当前无法提交时，触发冻结。冻结条件为下列任一成立（且该请求尚未提交）：

```text
s2Stuck = s1Valid && (
      respFifoFull                       // 命中响应无处安放
   || ( !hit && hitInMshr && !canMerge ) // 命中条目但已进入 FILL，暂不可合并
   || ( !hit && !hitInMshr && ( !hasFree || !hasAvailableWay ) )  // 无法分配
   || ( !hit && wbSameAddr )             // 需要淘汰但 WBB 同地址冲突（含 reserved）
)
```

冻结期间保持 Stage2 流水寄存器与输出不变、门控一切对外写、`cpuReady=False`、并保持读使能 `fire || s2Stall` 以刷新读数据。待条件消失后继续提交。

### 11.3 各反压来源详述

MSHR 相关反压保证"请求要么能合并、要么能分配新条目"；WBB 相关反压保证"脏行一定有地方写回"；响应队列反压保证"响应一定有地方安放"；可用 way 检查保证"未命中一定有路可换"。这些条件并行判定、共同合成最终的 `cpuReady`。

### 11.4 反压依赖图与无死锁论证

反压关系可归纳为：`cpuReady`/Stage2 冻结依赖 MSHR 状态、WBB 状态、响应队列状态、替换资源；MSHR 状态推进依赖内存响应；内存响应依赖总线；总线上的写回依赖 WBB；而 WBB 的写回**不依赖被阻塞的 CPU 请求**。因此依赖链上不存在"CPU 等待自己"的闭环。特别地，Stage2 冻结等待的都是一些**与 CPU 无关、必然推进**的事件（WBB 写回完成释放槽位、MSHR 条目重放完成释放路、响应队列被 CPU 取走）——只要 CPU 最终取走响应，冻结就必然能在有限时间内解除。

```text
  cpuReady / Stage2 冻结
     |
     +--> MSHR 状态 --> 内存响应 --> 总线 --> WBB 写回 --+
     |                                                    |
     +--> WBB 状态 -----------------------（不依赖 CPU）  |
     |                                                    |
     +--> 响应队列状态 ---（CPU 取走响应后释放）           |
                                                          |
   （没有回到 cpuReady 的环）<---------------------------+
```

### 11.5 端口仲裁

如 5.5 所述，在"2 读 + 2 写 + 真双端口 bank"的模型下，任一 bank 每拍最多两次访问、恰落在两个端口上，因此正常路径无需同 bank 仲裁。唯一的兜底规则是：命中写（W1）与填充写（W2）若在同一个 bank 上相遇（仅在非 TDP 或极端情况下），W2 优先、W1 顺延并由 Stage2 冻结保持。若后续改用单端口或 1R1W 的低成本存储体，则启用附录 15.2 的备选仲裁表。

### 11.6 内存端口仲裁

读通道由 MSHR 独占发起，ID 取条目位次；写通道由 WBB 独占发起，ID 取缓冲区位次。两通道彼此独立，可同拍各自响应；内存每拍最多返回一个读响应和一个写响应，但读写可以同时响应。

## 12. 时序图汇总

### 12.1 命中读（2 拍内部延迟）

```text
  周期      T          T+1         T+2
  cpu.valid #####
  cpu.ready #####
  Stage1    接收/分解/发读地址
  Stage2                比较/选数据/返回
  cpuReadResp                       #####
```

### 12.2 命中写（CPU 2 拍收到响应，存储体第 3 拍生效）

```text
  周期      T          T+1         T+2         T+3
  Stage1    接收/分解/发读地址
  Stage2                比较/驱动单字写/返回写响应
  cpuWriteResp          #####
  存储体写入生效                     （时钟沿生效）
```

### 12.3 未命中淘汰：三拍原子时序（含窗口裁决）

下表把"淘汰原子组"与"下一条请求"的相位对齐。设 A 是一条未命中请求（其 Stage2 在周期 N），B 是紧随其后的一条请求（其 Stage1 在 N、Stage2 在 N+1）。

| 边沿 | A（Stage2 在 N） | B（Stage1 在 N、Stage2 在 N+1） |
| --- | --- | --- |
| N | 组合选 victim；组合准备 Way Lock、WBB 预留+写 addr、清 valid、分配 MSHR、读 victim 整行 | Stage1：发出 tag 读地址 |
| N→N+1 | 上述动作作为**原子组整体生效** | — |
| N+1 | 条目处于 SEND（总线接受后转 MISS_WAIT） | Stage2：用 N 拍快照比较，读到 `wayLocked=1` → 未命中；尝试分配；并**重查 WBB 同地址（含 reserved）** |
| N+1→N+2 | — | 若分配，则 B 的条目生效 |

要点：

- 淘汰原子组的全部使能条件必须在 **N 拍组合可知**（有空 WBB 槽、有空 MSHR 条目、有可用 way、非 TDP 时的 R2 bank 可用）；否则会出现"锁已置位而组被中止"的锁泄漏。
- `wayLocked` 与原子组同沿（N→N+1）生效，使其在 **N+1 对 B 的 Stage2 可见**，从而挡住 B 对 victim 行的假命中。
- 若 B 因 `!wayLocked` 被判为未命中而尝试去内存读同一行数据，则其同拍必须看到 A 的 WBB 预留（addr 已在 N→N+1 写入）——因此 N+1 的 WBB 同地址重查必须覆盖 `reserved`，冲突则冻结等待写回完成。这样，B 读到的一定是写回之后的最新数据。

### 12.4 未命中且 MSHR 命中（合并）

```text
  周期      T          T+1
  Stage1    分解/MSHR 匹配
  Stage2                提交：可合并（SEND/MISS_WAIT）→ 并入 Slot
                        不可合并（FILL）→ Stage2 冻结
  随后：等待该条目填充并按序重放（响应按原始顺序产生）
```

### 12.5 WBB 写回

```text
  周期      T              T+1              T+2 ...        收 memWriteResp
  WBB      预留+写addr      push data        轮询选中发写请求   释放
  状态     {reserved=1}    {valid=1}        {valid=1,issued=1} {空}
```

### 12.6 命中写在淘汰窗口的裁决（旁路）

写请求命中时，其写入与紧随其后的读若目标一致，采用 6.6 的读旁路；若写请求恰与某条未命中淘汰动作的 victim 行同地址，则由 `!wayLocked` 把该写请求改为未命中并走 MSHR（写分配），从而避免"写落入正在被淘汰的行而被丢弃"。

## 13. 不变量与假设清单

以下不变量在正常运行时应恒成立，可作为设计检查与验证的参考清单：

第一，若某 MSHR 条目有效且处于 SEND/MISS_WAIT 状态，则其对应的 Cache 行在填充完成前不应被标记为有效。第二，Cache 命中与 MSHR 命中不会对同一请求同时成立：填充后该行虽有效，但其路仍处于 Way Lock 下，命中判断因 `!wayLocked` 而不成立。第三，WBB 中同一地址至多存在一个条目（含 reserved），且同地址的未命中填充必须等该写回完成。第四，被 MSHR 占用的路一定处于 Way Lock 保护下，不会被替换选中。第五，MSHR 条目只有在其所有 Slot 重放完毕后才被释放，Way Lock 也只在此时清除。第六，写入 WBB 的脏行数据在被清除 valid 之前必须已完成预留（保证有槽可放）。第七，淘汰原子组的使能条件在 Stage2 组合可知，保证不会出现"锁已置位而组被中止"。第八，所有 CPU 访问均按字对齐，所有内存访问均按块对齐。

此外，本设计作如下前提假设：CPU 每周期最多发出一个访存请求；内存支持多个未完成事务且可能乱序返回，每拍最多返回一个读响应和一个写响应（读写可同拍）；同一时钟域、同步复位；响应允许乱序返回。

## 14. 待解决项与后续工作

第一，**CPU 请求 ID 位宽**尚未最终确定。当前暂定 12 位；建议由外部决定，或按"MSHR 条目数 × 每条目最大挂起数"推导最小位宽，并明确内部条目位次、总线 ID、WBB 位次三者之间的零扩展与截取、匹配规则。

第二，**替换策略的具体微架构实现**（随机/FIFO/LRU/PLRU）与 LRU 复位值待补充；onHit/onFill 的触发契约已在 10.3 确定。

第三，**异常处理**（内存响应错误、超时、非法 ID）暂不考虑，后续可扩展。

第四，**持续命中的重放饥饿**：目前命中响应优先于重放响应；若重放被长期饥饿，可引入一个"饥饿计数"机制——当重放被命中压制超过设定周期后，临时提高重放优先级，处理完再清零。当前为简化设计，暂不实现，记录待办。

第五，**端口模型的降本选项**：当前使用真双端口 bank；若因面积/功耗需要改用单端口或 1R1W 存储体，需按附录 15.2 启用备选仲裁，并补充相应时序说明。

第六，**WBB 与 MSHR 同地址检查的粒度**：当前采用 Stage1 检查 + Stage2 重查（含 reserved）；检查范围是否为全部条目、以及是否需要更细粒度，待实现时确认。

## 15. 附录

### 15.1 术语表

| 术语 | 含义 |
| --- | --- |
| MSHR | 未命中状态保持寄存器，记录并合并未完成访存 |
| WBB | 写回缓冲，暂存并异步写回被替换的脏行 |
| Entry | MSHR 中对应一条 Cache 行的条目 |
| Slot | MSHR Entry 内单个待处理请求 |
| SEND | MSHR 条目状态：已分配但尚未把读请求送上总线 |
| Fill | 从内存取回整行并写入 Cache |
| Replay | 把 MSHR 中挂起请求按序返回给 CPU |
| Reserved | WBB 槽位已被预留、数据尚未写入 |
| Way Lock | 锁定正在被处理的路，防止被替换 |
| Bypass | 旁路，用较新数据替代旧数据 |
| RAW | 写后读冒险 |
| Stall | Stage2 冻结，暂时停住流水并反压 Stage1 |
| Hit-under-miss | 未命中未完成时仍可服务其他命中请求 |
| MLP | 内存级并行度 |
| TDP | 真双端口存储体 |
| LRU / PLRU | （伪）最近最少使用替换策略 |

### 15.2 备选端口仲裁表（非 TDP / 单端口 bank 时使用）

说明：本表仅在后续改用非真双端口（如单端口或 1R1W）存储体、出现同 bank 端口竞争时启用；当前 TDP 模型下无需仲裁，本表仅作备用参考。

| 端口 | 请求源 | 优先级 | 冲突对象 | 仲裁规则 |
| --- | --- | --- | --- | --- |
| 读通道 R1 | 流水线字读 | 1（最高） | — | 关键路径，不可被抢占 |
| 读通道 R2 | victim 整行读 | 2 | 与 R1 同 bank 时 | R1 优先，R2 随淘汰原子组一并重试 |
| 写通道 W1 | 命中单字写 | 2 | 与 W2 同 bank 时 | W2 优先，W1 顺延 + Stage2 冻结 |
| 写通道 W2 | 填充整行写 | 1（最高） | 与 W1 同 bank 时 | W2 优先 |
| 清零通路 | victim 清 valid | — | 无 | 只写有效位存储体，不参与仲裁 |

特别说明：R2（victim 整行读）属于淘汰原子组的一部分，若因端口冲突无法当拍完成，**不能只挂起 R2**，而应让整个淘汰原子组一并重试（保持 victim valid、Stage2 冻结），否则会出现"valid 已清而脏数据未读出"的丢数据。这一点在 TDP 模型下不会发生，但改用单端口 bank 后必须遵守。
