# 带 MSHR 的 DCache 验证点

版本：v2.0；更新日期：2026-11-16。

本文由原《Cache IP 验证方案》整理为可逐项执行、登记证据的验证点清单。
覆盖当前实现支持的功能及关键边界；待确认行为单列，不能用当前 RTL 的输出反过来定义正确性。
不再保留旧文中的环境选型、里程碑和示例 SVA 伪代码。

## 1. 使用约定与范围

验证对象为 `Design/DCacheMSHR` 下的 SpinalHDL 实现：`WriteBackBuffer`、`Mshr`、
`CacheMem`/`Ram2R2W`、FIFO/LRU/tree-PLRU，以及 `DCache` 顶层。
模块边界以当前 Scala 接口为准，生成 RTL 也须核对，避免源码与生成文件版本不一致。

| 层级 | 含义 | 驱动与检查边界 |
| --- | --- | --- |
| 模块 IP | 独立验证 WBB、MSHR、CacheMem、Policy 或 FIFO | 直接驱动模块端口；上游合法性是明确假设，模块输出由独立模型检查 |
| 集成 | 验证 DCache 顶层及模块间交互 | CPU/内存合法流量为主，辅以内部事件和不变量；检查跨拍窗口与端到端数据 |
| 模块 IP + 集成 | 两层都必须覆盖 | 模块证明局部契约，顶层证明接线、使能、生命周期与仲裁遵守契约，不能二选一 |
| 配置检查 + 集成 | 参数约束、生成与不同配置运行 | elaboration负例、合法配置编译、相应功能回归 |
| 环境自检 | 验证 TB 自身 | 协议、模型、采样、检查器、超时和回归判定，不能算 DUT 功能通过 |

优先级：P0 为功能/协议正确性和数据安全必测；P1 为重要边界、并发、配置及资源利用；
P2 为扩展性能统计。每行的“检查内容与通过条件”是验证目标，**不是当前实现已通过的结论**。
`未闭合` 表示尚未具备该点完整的实现、覆盖和可追溯结果，包含已有部分实现的情况。
编号在本版内唯一；旧版编号已重新组织，不沿用旧编号与含义的隐式对应关系。

模块测试的合法输入前提也必须有 TB 断言：例如 MSHR 只接受针对可合并 Entry 的 merge，
WBB push 只能指向先前已预留槽，alloc 不得将同一 set/way 交给两个有效 Entry。
顶层集成验证负责证明它实际满足这些前提，不能要求子模块替上层自动纠错。

当前外部接口共七条 Stream；CPU 请求每拍至多一笔、字对齐；内存请求块对齐。
CPU ID 在对应响应握手前不复用，读写内存 ID 命名空间独立。无全局响应顺序保证，
数据期望按 CPU 请求接受顺序建立，读写两个响应通道按类型/ID 各自匹配。
单 Entry 的 Slot 重放握手按 Slot 顺序；这不等于读写响应在 CPU 两端口上必须全局按序握手。

不在当前 DUT 必测功能范围内：非对齐、字节使能/部分写、AXI 封装、总线错误/异常上报、
硬件超时处理、ECC、多核一致性、原子操作、随机替换策略、单写口降本方案、未实现的饥饿计数。
不为未定义非法输入编造“不能挂死”等通过要求；测试平台 watchdog 仍必须实现。

本版纠正旧方案中的下列要求：

1. 默认地址为 tag[31:11]/index[10:6]/wordOff[5:2]/byte[1:0]；不再使用错误的高位 index 划分。
2. 当前生成 RTL 是异步高有效 reset，TB 的低有效 rst_n 经取反接入；不要求未初始化 RAM 清零。
3. Stage2 冻结只禁止该请求的提交副作用，后台 fill/replay/WBB 必须继续推进以解除等待。
4. 行内 Slot 顺序和 CPU 两条响应通道的可见握手顺序分开检查，允许读写通道因独立反压交错。
5. 队列排空不代表脏行已落内存；无 flush 接口时使用合法驱逐并跟踪完成，不能把 CPU 全地址读回当作 flush。
6. 固定优先级下不声称任意无限负载无饥饿；活性检查显式约束停止新请求、最终 ready、最终返回响应。
7. “复位期间所有输出静默”“请求当拍零延迟返回”“同址读写原语固定先读/先写”等未确定行为不作为默认已知保证。

## 5. 待确认契约与专项风险

下表是依据本次源码阅读发现的契约边界/风险，尚未用专项用例证明为 RTL 缺陷。
这些问题不应因文档列出验证目标而被视为已经解决；合法输入下违反既定 Stream 契约仍应报失败。

| 编号 | 内容 | 关联验证点 | 处理与判定 |
| --- | --- | --- | --- |
| Q-01 | WBB send 和 MSHR replay 当前由候选集合及 rrPtr 组合选取，未见独立的挂起选择锁存；反压期间新增更靠前候选可能改变输出 | IF-002/003、WBS-002、MSC-013 | 增加“反压 + 新候选”模块定向和稳定性断言。MSHR memReadReq 已有 sendHold，不能由此推定另两条流也安全 |
| Q-02 | MSHR fill.en/fillReady 是自定义使能接口，顶层 fillReady 固定 True；模块可直接反压但多个候选时保持选择的契约未明确 | MSC-005/006 | 先确认是否要求 enable挂起时payload稳定；无论哪种契约，未接受不得丢事件、置fillDone或提前replay，顶层固定ready场景单独闭合 |
| Q-03 | memReadReq握手与对应memReadResp同拍时，响应处理只接受原状态MISS_WAIT，SEND当拍响应可能未登记 | IF-009、MSB-013 | 常规TB使用至少下一拍返回；若外部协议允许零延迟，须补支持/断言并跑同拍用例；不能默认为已支持 |
| Q-04 | 运行中复位后的迟到读写响应、CPU ID复用以及已接收写的取消语义未统一 | RST-010、IF-010 | 系统须约定清空后端pending、隔离epoch或等效措施。仅清DUT状态不足以安全接收旧ID响应；未定义前不声称热复位通过 |
| Q-05 | RAM同址read-during-write和W1/W2非法同址双写的接口约定需要固定 | MEM-015/016、PIP-002 | 顶层以锁避免双写，以旁路/刷新保证读值；模块仅按选用存储原语的明确语义判定，不靠仿真偶然值 |
| Q-06 | 同set同拍onHit/onFill对LRU/PLRU状态两次更新，当前实现后调用onFill优先，可能丢失命中更新 | POL-015 | 确认接受此策略近似或要求顺序合成；独立模型按确认结果检查，数据正确性仍不可放松 |
| Q-07 | 低位优先发送/填充、命中优先重放可能在无限新流量下饥饿；当前无饥饿计数 | INV-010、PER-008 | 有限候选/停止新增下检查进展；持续负载记录等待分布。若要求严格公平，先修改规格和实现 |
| Q-08 | NUM_BUS_OUTSTANDING用于ID位宽/约束，但未见读写总量共享额度控制；若设为小于Entry+WBB，不能仅凭参数名断言总量受限 | CFG-012 | 明确该值为每通道ID空间还是共享容量。共享上限由接收方ready或DUT额度管理保证后，再设置对应断言 |
| Q-09 | DATA_WIDTH/8使用整数除法，缺少显式DATA_WIDTH%8==0可能允许无效字宽通过部分require | CFG-008 | 补参数负例确认；将整字节宽和支持字宽列为约束完整性检查，文档不替代实现修复 |
