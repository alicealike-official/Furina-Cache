# DCache顶层验证case规划

版本：v2.0；日期：2026-11-25；状态：公开IO与分层IP检查已接入，本轮新增18个定向/随机case，112组完整回归通过。最新逐点状态以[主表](DCache顶层验证.md)为准；下方历史回归记录保留原始结果。

本文件依据[顶层验证点](DCache顶层验证.md)、[Cache架构spec](../../Architecture/Cache架构设计文档v2.md)、[MSHR接口spec](../../Architecture/MSHR_IP架构设计文档.md)和[WBB接口spec](../../Architecture/WBB_IP架构设计文档.md)编写。没有阅读DE实现；历史连接说明只帮助理解接口职责，不把其中的实现现状当成规格。

## 1. 当前范围与已有结果

当前验证固定规格DCache的CPU侧和内存侧整行V-R接口：32位CPU字、32位地址、64字节行、32组4路、4个MSHR Entry且每个4个Slot、4个WBB槽、5位CPU ID和4位内存ID。CPU每拍最多提交一笔请求，读写共用请求流；读写响应独立。内存响应最早下一拍，零拍不支持。复位目标为异步低有效。

本轮先规划正常功能；复位专项继续暂缓，热复位需先明确取消和旧响应隔离。AXI属于后续独立adapter，不纳入当前顶层case。不安排参数生成负例、跨容量回归或验证环境的递归验收点。

现有[UVM框架](../../verif_mshr/DCACHE_README.md)接入原C++ CacheTop和SparseMemory。[最初基础报告](../../verif_mshr/sim_dcache/work/framework/run_20261125_104508/summary.md)为默认空态及smoke各10 ns/4 ns共4/4 PASS，warning/error/fatal均为0。它证明框架和两读一写通路，不能直接证明命中、旁路、脏淘汰、满资源、乱序及全部复位场景。

## 2. 从公开IO能证明什么

| 可观察事件 | 能直接检查的内容 | 不能直接推定的内容 |
| --- | --- | --- |
| CPU请求握手 | 实际接受顺序、ID、读写类型、地址和数据 | 当拍是否分配Entry、是否命中、Stage2是否提交 |
| CPU响应握手 | 每个ID完成次数、读值、类型和完成时刻 | 内部入队时刻、具体FIFO占用或仲裁选择 |
| 内存读请求/响应 | 块地址、读ID、在途数、响应延迟和返回行 | CPU接受沿是否就是alloc/merge沿 |
| 内存写请求/响应 | 实际victim地址、整行版本、写ID、等待ack的窗口 | WBB预留/push的精确沿、内部槽状态位 |
| CPU ready变化 | 外部可见受阻及恢复 | 究竟由Entry满、way全锁、Slot满还是响应队列满导致 |

所有功能结论优先从这些IO及原始操作记录获得。用受控预热、暂停响应、实际请求计数和对照场景缩小歧义；仍无法区分的内部子条件保持未证明，不通过参考模型内部状态替代DUT证据。当前已增加只读模块接口及架构状态探针，直接检查集成窗口；尚未观察的RAM副本/recency等实现细节单列依赖范围，不以CPU结果代替。

## 3. 公共方法与需要扩展的环境能力

当前driver支持逐笔及连续每拍提交。内存代理支持FIFO/逆序/随机选择、周期延迟和接收开关；CPU读写接收支持独立开关及有界随机抖动。连续提交、按ID乱序、无效载荷扰动及场景计数均已接入。test和sequence仍按下面的职责分工。

- test负责配置、启动、等待和通过条件；sequence负责数据、地址、请求排列及调度；公共提交、计数和收尾工具放base，不在每个test复制。
- 时钟配置只由TB顶层创建并逐级传递。所有延迟、阻塞和超时以拍为单位，至少在10 ns/4 ns运行。
- 继续使用原C++ CacheTop逐拍预测和原C++ SparseMemory后端。没有计划再写一套Cache行为模型。原始激励期望用于检查CPU语义和数据版本，不模拟内部替换/流水状态。
- 预置数据在CPU访问前写入外部SparseMemory。CPU写只更新独立的架构期望记录，真正外部MEM只由实际写回更新，两者不能共享一次写操作。
- CPU读接受时按先前接受的CPU写保存期望值，后续写不能改掉旧读期望；响应按类型和ID匹配。写回记录必须对应当时victim版本，不能用测试末尾的新值比较早期写回。
- 一个ID直到CPU响应被接受之后才能复用，不按MSHR释放或内部入队提前复用。不同内存读ID与写ID分别管理；响应源保持载荷直到握手，禁止未发先回或重复响应。
- 场景计数取实际事件，不能只检查sequence发出了多少item。每个case必须同时通过数据/协议检查和必要场景命中检查。
- 发现确定的DV问题可修环境后重跑；确定为DE或归因不明时保留失败、最小IO轨迹及日志，不改设计、模型或检查规则迎合结果。Spinal自带测试不作为验证依据。

CPU和MEM实际已接受事务数对得上只表示没有遗留义务，不能说明所有脏Cache行已回写。收尾分为两类：普通case等待CPU及已发内存事务结束；验证后端一致性的case另外驱逐受测行、确认对应ack，再比较MEM。当前没有flush接口，不凭空要求全Cache清空。

## 5. 各case怎么运行、怎样算通过

<a id="c01"></a>

### C01 基础读写通路

- 激励：沿用现有0x1000读→写0x12345678→再读，CPU ID分别为0/1/2。
- 检查：两次读分别为0和新写值，一次写响应，所有ID和类型正确。原case未等待首读完成，不应直接声称后两笔必为命中。
- 必须命中：实际接受3请求、2读响应、1写响应；若要闭合DCT-001的冷读后命中子条件，应补首读完成后再写读的阶段，并核对内存读1次、写回0次。
- 主要验证点：DCT-001、DCT-008。

<a id="c02"></a>

### C02 预热后各组各字命中

- 激励：通过CPU读填入各组不同tag的行，等预热完成；逐字读、写、再读，使用可区分数据。
- 检查：只有目标字变化，同行其他字保留；预热后的命中阶段无新增内存读。
- 必须命中：32个set、16个word位置均访问；在固定替换策略下填满4个不同tag，不把逻辑tag编号当作实际way证据。
- 主要验证点：DCT-002、DCT-003、DCT-014、CFG-002、CFG-005。

<a id="c03"></a>

### C03 冷写分配与未写字保留

- 激励：预置外部MEM整行不同数据，CPU写一个尚未缓存的首字/末字，再遍历整行读取；最后制造冲突写回。
- 检查：冷写取回原行，只覆盖目标字；CPU和实际写回整行都保持其他字正确。
- 必须命中：首末字各一次冷写；每个生命周期一次内存读；实际写回包含新字及原行其余字。
- 主要验证点：DCT-004、DCT-005、EVI-018。

<a id="c04"></a>

### C04 数据位与字节顺序

- 激励：sequence生成全0、全1、逐字/逐字节、交替位、单1/单0遍历和随机数据；覆盖填充、命中写、合并写及淘汰。
- 检查：逐次CPU读和实际写回均与原始记录一致；纯读检查与混合写分开，避免写覆盖掩盖原位错误。
- 必须命中：单1/单0各遍历512位；每个字位置和各数据类型都有实际接受事件。
- 主要验证点：DCT-013、CFG-005、EVI-018。

<a id="c05"></a>

### C05 连续写后读与旁路

- 激励：预热目标行，按无空拍CPU提交W-R、W-W-R、W-R-W-R；另变更tag/index/word防止错误旁路。
- 检查：每个读只看到此前接受的最近写，同字旁路正确，异址不能使用旧写值；冻结后恢复也保持结果。
- 必须命中：相邻采样沿实际CPU握手，不能仅由sequence连续调用判定无气泡；无冻结及有冻结分别命中。现driver需先支持连续提交。
- 主要验证点：PIP-001、PIP-002、PIP-003、PIP-004、PIP-005、DCT-006、DCT-007。

<a id="c06"></a>

### C06 地址分界与ID边界

- 激励：覆盖首末set、首末word、tag高位翻转与相邻行地址；使用ID0、最大值和非连续ID，完成后再复用。
- 检查：内存块地址、返回字和CPU ID正确，不因截断误命中；所有CPU地址仍整字对齐。
- 必须命中：各地址字段边界都有接受和正确返回；至少一次ID完成后的再次使用。
- 主要验证点：CFG-002、CFG-003、CFG-004、DCT-010、DCT-014。

<a id="c07"></a>

### C07 同行合并与读历史

- 激励：暂停内存响应，在同一行提交RR/RW/WR/WW及R-W-R-W等序列，包含同字/异字、首末字；放行后读取并驱逐。
- 检查：每行只发一次内存读；每笔读保留当时应见值，最终填充/写回使用全部写的最后版本。
- 必须命中：每组同址请求实际已接受且仍在等待响应；读写组合分别计数，不能用后来命中替代合并。
- 主要验证点：DCT-006、DCT-007、PER-003、EVI-018。

<a id="c08"></a>

### C08 未命中等待时其他行先完成

- 激励：先预热热行并排空，再对不同冷行发读，保持其响应；持续访问热行，然后放行冷行。
- 检查：资源充足时热行请求可在冷行响应前完成，冷行最终也正确完成。
- 必须命中：至少一笔热行响应早于被延迟冷行响应；不能用两个冷行的乱序返回代替命中证明。
- 主要验证点：PER-001、DCT-009。

<a id="c09"></a>

### C09 多行未命中与Entry满

- 激励：对不同set提交4个冷块，保持内存响应；向旧块追加合法请求，再尝试第5个冷块，释放一条后恢复。
- 检查：实际内存读在途达到4但不超过4；满表仍可同行合并；等待的新请求不丢不重复。
- 必须命中：4笔不同ID读未完成、满表期间同行请求接受、额外请求受阻与释放后完成。CPU可能先缓存在流水中，不能把cpu.ready时刻直接等同Entry分配。
- 主要验证点：CFG-012、PER-002、PER-004、PIP-009。

<a id="c10"></a>

### C10 同行Slot满与响应截止边界

- 激励：保持一条冷行未完成，提交4笔同行请求，再提交后续请求；分别在发送受阻和已发等响应阶段组织，随后放行。
- 检查：超过Slot容量的请求不能覆盖旧请求；进入fill后也不能误追加。后续请求在条件允许后正常完成。
- 必须命中：四笔已接受同行请求共用一次内存读，后续请求受阻/恢复；精确merge与响应同沿无法仅靠CPU接受沿确认时保留限制。
- 主要验证点：PIP-010、PIP-016、PER-003。

<a id="c11"></a>

### C11 同set锁住与解锁后访问

- 激励：对同set不同tag发起未命中，保持响应或CPU接收；再访问旧未完成行及需要新路的冲突行，逐笔放行后复查。
- 检查：锁住的行不能假命中、被再次淘汰；完成后原行正常可访问，不重复创建无谓读事务。
- 必须命中：同set冲突等待、最后响应完成后恢复、不同set对照访问。当前Entry数等于way数，全路锁与Entry满可能重合，不能仅凭停顿区分原因。
- 主要验证点：LCK-001、LCK-002、LCK-003、LCK-004、LCK-005、LCK-006、LCK-007、LCK-008、LCK-009、LCK-010、PIP-011。

<a id="c12"></a>

### C12 干净行和无效行替换

- 激励：从空Cache填满一个set的干净行，再访问冲突tag；重复使用原先清valid的位置。
- 检查：干净或无效victim不产生内存写回；新行数据正确，残留dirty不能触发多余写回。
- 必须命中：实际发生超出4路容量的冲突替换；整个干净阶段写请求数为0。
- 主要验证点：EVI-001、DCT-012、POL-001。

<a id="c13"></a>

### C13 脏淘汰地址与整行数据

- 激励：填满同set多条行，分别修改多个字，再用冲突行触发淘汰；记录实际写回地址，不假定每种策略的victim相同。
- 检查：写回使用旧tag和set，整行包含当时最新修改；新行正确填充，其他行不被误清。
- 必须命中：实际脏写回、正确块地址和完整64字节数据；高低tag可区分，读回驱逐后的旧块。
- 主要验证点：EVI-002、EVI-004、EVI-005、EVI-018、DCT-011。

<a id="c14"></a>

### C14 刚写脏行紧接着淘汰

- 激励：连续CPU提交命中写及冲突未命中，再紧跟对旧行的读或写；另安排等待中的fill与新请求交错。
- 检查：刚写的数据必须进入写回；不能因旧valid/dirty快照假命中或漏写回，后续CPU结果按接受顺序正确。
- 必须命中：紧邻CPU握手且实际淘汰同一旧块，分别命中写后淘汰、淘汰后读、淘汰后写；内部Stage相位仅有外部轨迹时不声称逐寄存器证明。
- 主要验证点：EVI-007、EVI-008、EVI-012、EVI-013、EVI-014、PIP-017。

<a id="c15"></a>

### C15 写回完成前禁止同址读

- 激励：先触发旧块脏写回，分别阻塞写请求接受和写响应；在两个阶段对旧块发读，最后返回ack。
- 检查：新同址内存读不得早于对应写完成；等待期间无关事务可继续，最终读到完整新版本。
- 必须命中：写请求握手后仍有一段无ack窗口，其中同址读请求未发出；ack后才观察到同址内存读。预留到push窗口仍需单独证据。
- 主要验证点：EVI-009、EVI-010、EVI-011、EVI-016、PIP-012。

<a id="c16"></a>

### C16 WBB满与后台进展

- 激励：预热并弄脏足够多冲突行，逐笔淘汰并保持写响应，直到4笔写回未完成；再发需要淘汰的请求，释放一个写ID。
- 检查：在途写回不超过4；受阻请求保留，释放后完成；已有无关读响应和CPU响应不能一起被停住。
- 必须命中：4个不同写ID未完成、额外请求等待、单个ack后恢复；其他事务在等待期间实际完成。
- 主要验证点：EVI-003、EVI-019、PIP-013、INV-008、PER-007。

<a id="c17"></a>

### C17 内存请求反压与恢复

- 激励：分别长期拉低读请求ready、写请求ready及同时阻塞；载荷呈现后继续制造其他候选，再放行。
- 检查：DUT输出valid和地址/ID/整行保持到握手，恢复后只处理一次，读写方向互不串扰。
- 必须命中：两方向各有valid&&!ready持续至少8拍并恢复；同时阻塞与分开放行都命中。
- 主要验证点：IF-001、IF-002、IF-004、RND-007。

<a id="c18"></a>

### C18 CPU响应队列满与恢复

- 激励：预热后发足够多命中读或写，分别拉低CPU读ready、写ready及两者；让队列填满后逐步放行。
- 检查：挂起响应保持，不能覆盖旧ID/数据；阻塞传回请求侧，放行后响应按各自队列顺序完整返回。
- 必须命中：三种阻塞方式均观察到有效响应等待及CPU请求受阻；只堵一边时检查架构规定的整体准入限制。
- 主要验证点：RSP-001、RSP-002、RSP-003、RSP-004、RSP-005、RSP-009、RSP-010、PIP-014。

<a id="c19"></a>

### C19 命中响应与replay竞争

- 激励：保留一个未命中待返回，准备热行命中流，控制内存返回时机；分别组织读/读、写/写、读/写和写/读。
- 检查：CPU端结果、类型与ID正确；同类竞争不得丢失replay，异类可各自返回，不强加读写通道之间的全局顺序。
- 必须命中：CPU双响应同沿、同类来源均最终完成；命中优先和内部入队同沿是否发生不能仅从两个CPU输出推定，必要子项保持未证实。
- 主要验证点：RSP-006、RSP-007、RSP-008、RSP-012、IF-003。

<a id="c20"></a>

### C20 读写内存同时进行

- 激励：制造脏写回和不同块冷读，分别控制请求ready及两类响应放行时刻，包含数值相同的读写ID。
- 检查：读写ID空间独立，读数据与写回行正确；不能因为等写ack就停止无关填充。
- 必须命中：读写请求同沿、读写响应同沿以及同值ID并存；未命中某组合时补定向调度。
- 主要验证点：IF-007、CFG-006、EVI-017、EVI-020、EVI-021。

<a id="c21"></a>

### C21 按ID乱序返回与复用

- 激励：累计多笔实际内存读/写请求，分别以逆序和指定ID返回，再用CPU完成后的ID发新请求。
- 检查：CPU结果按ID匹配，跨行允许乱序；任何通道不重复接受响应或过早复用ID。
- 必须命中：至少两笔读乱序、两笔写乱序、相邻拍不同ID响应及CPU ID复用。需扩展当前FIFO内存driver。
- 主要验证点：DCT-009、DCT-010、INV-006。

<a id="c22"></a>

### C22 最快与可变内存延迟

- 激励：在无排队阶段逐笔设置1/2/7/32拍读返回和写ack，再加入多请求竞争和随机延迟。
- 检查：按真实请求/响应握手计算延迟；无阻塞精确等于设置值，有阻塞不早于设置值，最终CPU数据正确。
- 必须命中：读写两方向每个固定延迟均实际命中，正常profile不生成零拍。
- 主要验证点：IF-009。

<a id="c23"></a>

### C23 顶层多个接口事件同拍

- 激励：使用CPU请求、CPU读/写响应、内存读/写请求与响应这些公开事件组织并发；先覆盖读写双请求/双响应，再叠加CPU接受。
- 检查：各事务的ID、数据和完成计数都正确，原请求不会因别的通道事件丢失或重复。
- 必须命中：逐个记录实际同沿事件掩码；合法组合在实现case时列成有限清单，不能只用随机运行无报错证明全部覆盖。
- 主要验证点：IF-007、INV-004。

<a id="c24"></a>

### C24 多个阻塞原因与长等待恢复

- 激励：先保持写ack和CPU响应ready等不同阻塞，再依次解除其中一个，最后全部放行；最长等待先定为128拍。
- 检查：尚有实际阻塞时不能丢失当前请求；阻塞源的后台动作能继续，最终完成原来的请求。
- 必须命中：128拍等待、只解除一个条件的中间窗口、全部解除后的排空；内部原因位不作强制探测。
- 主要验证点：PIP-006、PIP-007、PIP-008、PIP-015、PIP-020、INV-008、INV-009、RND-011。

<a id="c25"></a>

### C25 替换策略在顶层的可见结果

- 激励：先验证当前FIFO：填入同set四条行，反复命中最老行，再插入新tag并从实际写回/再访问缺失判定victim。LRU/PLRU另设构建profile。
- 检查：victim符合已确认策略且跳过锁定路；不把模型内部顺序当作观测到的DUT状态。
- 必须命中：FIFO命中不改变淘汰顺序、填充更新顺序、无效未锁路优先；其他策略须先有明确生成及模型选择入口。
- 主要验证点：POL-001、POL-002、POL-003、POL-004、POL-005、POL-013、POL-014、RND-009。

<a id="c26"></a>

### C26 无效载荷不产生事务

- 激励：空态及有请求未完成时，令CPU valid和内存响应valid为0，改变对应地址、数据和ID；保持有效事务不变。
- 检查：无效字段不引起新内存请求、CPU响应或已有数据变化，最后正常完成原事务。
- 必须命中：空态/占用态均命中三个输入通道的无效载荷变化；当前driver需显式扩展该模式。
- 主要验证点：IF-006、IF-008。

<a id="c27"></a>

### C27 连续命中吞吐与可见延迟

- 激励：预热并排空，在ready持续为1且无资源限制时连续128拍提交命中请求；读、写和混合分别运行。
- 检查：稳态应达到每拍接受一笔；CPU响应最终守恒。只测公开接受到响应的延迟，不伪称观察内部入队时间。
- 必须命中：至少128个连续实际CPU握手；需扩展driver去除准备空拍，不能用当前driver结果给DUT定性能结论。
- 主要验证点：PER-005、PER-006、PIP-001。

<a id="c28"></a>

### C28 逐次写回及最终内存检查

- 激励：对有限地址集写多轮不同值，用合法冲突访问逐出受测脏行，跟踪实际写回地址/版本并等待ack，随后CPU再读。
- 检查：每次写回比较当时版本，所有受测旧脏行确认写回后才比较后端最终值；辅助驱逐行可能仍脏，不要求整个Cache为空。
- 必须命中：受测地址各自有实际写回和ack证据；每次写回及最终回读均正确。
- 主要验证点：END-004、END-005、END-006、END-007、END-009。

<a id="c29"></a>

### C29 均匀、热点及同set随机

- 激励：分别使用均匀块、少量热点和超过way数的同set tag集合，随机读写、ID、请求接收、响应延迟及顺序。
- 检查：所有CPU结果与原始操作顺序一致，实际写回按当时版本核对，停止新增并放行后能完成。
- 必须命中：各profile初定至少4096笔已接受请求，必须命中冷读、写、合并可见证据、写回、反压及复用；未命中不能算profile完成。
- 主要验证点：RND-004、RND-005、RND-006、RND-007。

<a id="c30"></a>

### C30 最后资源与释放交叉

- 激励：复用Entry/Slot/WBB/响应队列压力场景，在最后可用位置、全满和释放恢复窗口对齐公开事件。
- 检查：各边界仍保持数据、ID和计数正确；不构造非法重复ID、重复响应或零拍返回。
- 必须命中：建立有限矩阵：满表同行接受、末Slot与内存响应、4写回未ack后释放、CPU队列阻塞后恢复；不能证明的内部精确容量/边沿单列待证。
- 主要验证点：RND-008。

<a id="c31"></a>

### C31 长期运行与重复使用

- 激励：使用热点和同set冲突混合流量，周期性完成受测地址驱逐检查；至少65536笔CPU请求/种子，初定3种子。
- 检查：长期数据正确、无ID或容量丢失；所有已接受事务最终完成，后端检查只针对确认驱逐的地址。
- 必须命中：每种子达到实际请求规模，至少8轮受测脏行驱逐与再使用，各轮有CPU和内存完成证据。
- 主要验证点：RND-010、INV-007、INV-010。

## 6. 依赖场景与暂缓内容

<a id="s01"></a>

### S01 复位：保留规划，暂不实现

启动、空闲重复复位、停钟异步复位、释放首拍/次拍请求和运行中复位分别登记。基础空态通过只证明这一启动轨迹。热复位必须先确定CPU取消、MEM旧响应和ID复用契约；实现阶段recovery/removal报告不能由UVM case替代。

<a id="s02"></a>

### S02 存储体依赖：已接入真实端口，副本实现另列

顶层C02/C04/C05/C13检查读取最新值、整行顺序、写后读和淘汰内容。Ram2R2W复制体、内部新旧选择标记及物理bank的具体同时访问，不能凭这些结果逐项断言已经发生。本轮已只读绑定CacheMem端口和元数据，以原C++ CacheMem核对真实读写历史；未新增独立CacheMem驱动环境。四端口独立组合、原始RAM副本与recency需要模块级场景，不读取DE行为逻辑猜测期望。

<a id="s03"></a>

### S03 策略依赖：当前先FIFO

FIFO的CPU可见victim行为由C25安排。LRU/PLRU可作为后续策略功能profile，前提是明确生成策略、原模型类型和Q-06同set双更新语义；不能仅修改test名就认为切换成功。当前FIFO顺序数组已只读接入并与原FifoPolicy逐拍比较；不涉及LRU/PLRU内部树位。无故丢数据即使发生在待确认策略边界也不能豁免。

<a id="s04"></a>

### S04 性能辅助记录

C27/C38测量CPU吞吐；本轮按真实ID记录接受、提交、入队和CPU取走三段延迟。其它仲裁等待和占用水位没有直接测量时，不能从模型值冒充实测。无明确spec阈值的分布只作为分析材料，不另设必须关闭的环境检查点。有明确性能要求时，再定义对应可观察量或另行约定探测方式。

| 阶段 | case | 完成依据 |

本规划没有把子模块已通过的场景直接标成顶层通过。既有逐拍C++比较与IO时序不一致时应先定位；只在明确架构允许可变响应时延并确定比较方式不合适后才能调整，不能把所有响应简单延迟一拍获得PASS。

## C50 存储端口组合补测

入口为`dcache_memory_combinations_test`。针对MEM-009、MEM-010、MEM-012增加实际组合统计和带覆盖要求的随机流量，复用原CacheMem逐拍数据检查，不另写行为模型。

| R1/R2访问同set、不同set | 2 | 两种关系分别有计数，数据继续逐笔比较 |
